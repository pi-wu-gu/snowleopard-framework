# 工具信息注入与逐级查询 · 可行性分析（2026-10-27 15:25 定稿 v4）

> 命题（用户原话）："添加核心侧工具功能：工具信息：自动注入工具组信息及落单工具信息，提供逐级调用能力，
> 提供搜索能力。注意在组内的工具信息不主动注入。确保模型能直接知道工具组列表及介绍、孤儿工具列表及信息，
> 同时对工具组有主动逐级查询能力，在知道工具路径后可主动调用工具。"
>
> 修订链：**v1** 形态取舍（A/B/C 三选一 + 宿主启发式）方向错误 → **v2** 按 14:56 裁决重写
> → **v3** 按 15:07 四条裁决定稿（完整目录 / `tool_scope` / 来源分类 + `solo` / 多组查询）
> → **v4（本版）** 全文校对：**落点归位到内核**——本条命题 80% 是 core 的新增，壳只做接线。

## 零、为什么分组设计完，仍然是"平铺大量工具"

直接回答此前的质疑：**不是照抄星期五的代码；恰恰相反——雪豹这套是自己写的，却把星期五已经解决掉的那套机制丢了。**

三条根因，按贡献排序：

1. **core 只做了数据面，没做工具面**。`briefs()` / `help()` / `search()` 三个方法齐全、注释写着"两级注入"，
   但**没有任何工具把它们的入口交给模型**。全仓 `tool_search` 只出现在错误提示里（`ToolRegistry` :224、
   `BuiltinToolkit` :361），`tool_help` 连提示里都没有。模型没有"主动查"的手段 → 唯一出口只剩 `tools` 数组。
2. **壳侧把"组"当成了代码组织，不是调用单元**。`skeletons()` 用组注册、`routeOrder()` 用组排序，
   但模型的世界里从来没有"组"这个对象：没有组清单、不能按组取用、不能按组停用。分组只活在源码里。
3. **于是只能全量兜底，再用排序打补丁**。79 个工具全量声明 → 模型对末尾视而不见 → 加 `routeOrder()` 排序
   → 排序只在脱机复测有效，真机仍漏（13:42 那次"工具表里没有截图操作"）。三步都在补第 1 步的缺失。

对照星期五：它有 SchemaTrimmer（按优先级裁剪 + UNLOCK_TOOL 永不裁 + 被裁清单可见）、
ToolExposure.pin（会话级解锁集）、ToolHelpTool（查用法即解锁，下一轮带签名）、
ContextAssembler 的 [tools] 块。**"no schema, no call" + "解锁可回"** 这一整套，雪豹一个都没有。
所以问题不是"照抄了旧做法"，而是**没把核心已经设计好的规则实到底**。

## 一、结论与落点总表

**可行。且这条命题的主体在内核**：把"组"从源码概念变成模型可操作的对象，是注册表与内置工具组的职责；
壳只负责"每轮向 core 要清单、按清单声明、把回执如实转达"。

| # | 要补的 | 落点 | 现状 |
| --- | --- | --- | --- |
| 1 | 注入块（分组用法 + 组清单 + 无组工具）生成 | **core**（新增 `injectionBlock()`） | 零（方法有，没人调） |

## 二、规范原文（这些条款早就写了，只是没实现）

`雪豹决策核心/docs/工具组支持可行性分析-2026-10-22.md` §一.1（原文）：

> "工具组或工具带自动注入简介 + 用法详解的统一查询入口 —— **可行**。星期五已有雏形：
> 清单 `summary`/`usage` 自动注入 + `tool_help` 统一入口。差别在草案要求**组级与工具级两条注入通道**
> ——组简介注入上下文（便宜），工具详解按需查（省 token）。这正是'单轮 92% 预算花在工具介绍上'的解法。"

> "工具组必须带简介，工具可选 …… 无 `summary` 的工具允许但查询入口回退显示 `（无简介，用 tool_help <name> 看详解）`"

> "工具组可选带详解，工具必须 …… 把详解定义为 `usage + params schema`（结构化字段），而非一整篇散文"

`内置工具组-2026-10-23.md` §一：

> "便宜的那份（每轮进上下文）= `briefs()`：分类 + 全名 + 组简介；按需的那份 = `help(name)`：组详解 + 每工具 usage/参数。
> **分界即省 token**：组简介进上下文，工具详解不主动注入。"

所以：**理解没错，规范是对的。** 错在两处：
- 实现侧：core 只写了方法没给工具面；壳侧没接，直接全量平铺（§零）。
- 规范侧：确实没写透两条——① 组详解要不要规定内容（功能 + 完整目录）？② 无组工具怎么处理？
  这两条在 §七 补成条款。

## 三、硬约束：声明 / 可见 / 可调是三件事

| 状态 | 模型知道名字 | 能可靠发出 tool_call | 我们能执行 |
| --- | --- | --- | --- |
| 只在组清单里（组名可见，工具名不可见） | 组名 ✓ / 工具名 ✗ | ✗ | — |
| `tool_help` 后拿到工具名与参数 | ✓ | 多数模型**不会**（未声明） | ✓ |
| 进 `tools` 数组 | ✓ | ✓ | ✓ |

推论：
- "组内工具信息不主动注入"成立的前提是**有逐级查询入口**，否则等于让模型猜。
- "查到就能调"在实现上成立（`TOOLS` 索引按全量注册表建），但**不稳定**；要稳定，必须让该组下一轮进 `tools`
  ——这正是"把组加入工作集"的技术含义。**多一轮，是这个方案的固有代价，不是缺陷**。
- 与星期五一致：`tool_help` 回执明写"已加入，下一轮请求将带上它的调用签名"。

## 四、设计（落点全部标注 core / 壳）

### 4.0 内核新增的四个部件

| 部件 | 位置（core） | 职责 | 为什么必须在 core |
| --- | --- | --- | --- |
| `ToolExposure` | `snowleopard/core/registry/ToolExposure.java`（新） | 按 caller_id 存工作集：`pin/unpin/active/isActive/clear` | 身份只有 core 有（`Ids.Caller`），放壳就等于壳自己造一套身份 |
| `injectionBlock()` | `ToolRegistry`（新方法） | 生成三块注入文本（用法 + 组清单按来源分节 + 无组工具） | 文案住 core，多宿主共用；放壳会各写一版，措辞必然漂移 |
| `members()` | `ToolRegistry`（新方法） | 组级视图：成员名 + 一行简介（**不含参数**） | `help()` 现在是"组 + 每个工具的 usage/params"，两级的价值就没了 |
| `ToolCatalogGroup` | `snowleopard/core/builtin/`（新） + `BuiltinToolkit` 加 `case "tool"` | 三个目录工具的执行面 | 与其余六组同一条注册与派发路径，不开特权通道 |

`CallerScope` 已具备条件：`SnowLeopard.forCaller(id)` → `CallerScope implements BuiltinHome` → `home.callerId()`。
壳侧 `BuiltinRuntime` 已按 modelId 缓存 scope（`SCOPES.computeIfAbsent(modelId, core::forCaller)`），
所以 `tool_scope` 在 core 内部就能知道"给谁加"，**壳一行身份代码都不用写**。

### 4.1 注入层（core 生成，壳只 append）

```
【工具的分组方式】
工具按"组"组织：组有名字、来源、功能说明和一份目录（组内有哪些工具）。
本轮只给你组清单；组内工具的用法不在这里，用 tool_help 查（知道组名就能查，可按组内目录只取其中一个）。
查过的组会加入本轮工具表，下一轮起可直接调用；不再需要时用 tool_scope remove 移出（省上下文）。

【工具组清单】20 组 · 按来源分节（跨来源重名用全名区分）
[builtin:core] 7 组
- builtin:core:session — 会话管理（不可禁用）：结束本轮、查看消耗与余量  (2)
- builtin:core:tool — 工具目录：列组 / 查详解 / 增删工作集  (3)
……
[mod:snowleopard] 13 组
- mod:snowleopard:move — 移动（三驱动/寻路/阻塞判定）  (6)
……

【无组工具】（按来源成组，标识固定为 solo；简介与用法直接给全）
- mod:snowleopard:solo — snowleopard · 无组工具（0 个）
```

规则：
- **按来源分节**：来源 = 限定名第二段（`builtin:core` / `mod:snowleopard` / 其他模组各一节）。
  跨来源重名是常态（谁都能起 `move`），注入**只写全名**；短名只由 `tool_help` 接受，歧义必须报错不猜。
- **组**：一行 = 全名 + 简介首行 + 工具数。**组内工具一个都不列**（命题的硬要求）。
  来源已在全名里，不再另打分类标签（重复）。
- **无组工具**：该组成员 `简介 + 用法 + 参数` 全量直给（没有下一级可查）。空则不占注入行。
- **用法说明是固定文案**，不每轮重算；写清"组是什么 / 怎么查 / 怎么取用 / 怎么移除"。
- 未启用组沿用 `briefs()` 的既有口径：只留名字（`（未启用，仅名称）`）。

体量：20 行 ≈ 1.4K 字符 + 用法说明 ≈ 0.4K + 无组工具 ≈ 0 → **约 1.8K 字符 ≈ 1.2K token**
（今天全量 79 工具 ≈ 7–9K）。

### 4.2 目录工具（core 内置第 7 组 `tool`，ALWAYS_ON）

| 工具 | 签名 | 行为 |
| --- | --- | --- |
| `tool_list` | `tool_list(source?)` | 组清单（全名/简介/工具数/启用态）+ 无组工具；`source` 支持 `builtin` / `snowleopard` / `mod:snowleopard`，按来源分节 |
| `tool_help` | `tool_help(targets)` | `targets` 逗号分隔、**上限 4**。`组` → 组详解（功能 + 完整目录）+ 成员清单（名字 + 一行简介，不含参数），并把该组**加入工作集**；`组.工具` → 完整 usage + params，只把**该工具**加入工作集（组内筛选）。短名仅无歧义时接受 |
| `tool_scope` | `tool_scope(add\|remove, target)` | 显式增删工作集：`add move` / `remove move` / `remove move.goto`；同样支持逗号与来源限定 |

命名理由：`tool_use` 会与 `interact/use` 混；`tool_scope` 自解释。暴露名必须让人猜到用途（`shot` 的教训）。
三个工具都 `ALWAYS_ON`——目录被禁用等于模型彻底失明（与 session/memory 同理）。

> 上限 4 是防"一次要 20 个组"退化成全量注入——**兜底靠上限，不靠自觉**。

### 4.3 工作集（core `ToolExposure`，按 caller_id）

- 键 = `caller_id`（core 注入，不可伪造）；`tool_scope` 执行时由 `home.callerId()` 取，**不接受 caller 参数**。
- 语义：`ACTIVE = 元工具组（永在） ∪ pin 过的组 ∪ 本会话调用过工具的组`。
- **只增不减，除非显式 `remove`**；`clear(caller)` 由**宿主在会话开始时调用**——
  会话边界是宿主的定义，core 不猜（与"RuntimeView 是运行态唯一权威"同源：core 只提供状态，不推断状态）。
- 壳侧 `AiHost` 每次 `converse()` 开头 `exposure.clear(model)`，之后每轮读 `active(model)` 出 `tools`。
- **裁剪必须可见**：未在工作的组仍在注入清单里留一行，模型不会以为它们不存在。

### 4.4 执行层

- core：`BuiltinToolkit.call` 加 `case "tool"`；三个目录工具直接调注册表现成方法（`briefs`/`members`/`help`/`search`）。
- 壳：`executeTool` 补一条话术——调用"已注册但未在工作集"的工具时**照常执行**，结果末尾附
  `（该工具所属组尚未加入工具表，需要的话 tool_scope add <组>）`。否则下一轮它又不在清单里，模型会困惑。

## 五、`routeOrder()` 退役（壳侧唯一的功能删除）

v1 曾推荐"宿主词表决定声明哪几组"，v2 已否。本版进一步定：**`routeOrder()` / `GROUP_HINTS` 一并删除**。

理由：工作集与路由是**两套决定"声明什么"的机制**，同时存在就是双源——双源必然漂移，漂移不报错只出错
（与"同一职责多实现"同源）。路由治的病（末尾视而不见）由"工作集外根本不在清单里"根治：
- 不在工作集 → 不进 `tools` → 不会"排在末尾被无视"，因为它根本不在；
- 在工作集 → 顺序按来源 + 注册序稳定输出，不需要按话题重排。

**保留的结论**：v1.12.10 的实测（模型对长清单末尾视而不见）仍然有效，它是本方案的前提之一；
只是**手段**从"排序"换成"裁剪+按需取用"。同时 `vision` 常驻第一的 hack 一并删除。

## 六、无组工具（`solo`）

1. **支持方式（不开第二条注册路径）**：`ToolGroupProvider.Descriptor` 增加"无组"语义
   （`groupId` 为空 + `source` 必填），装载时由**装载器**合成组 `<来源类型>:<来源ID>:solo`。
   与"限定名由装载器拼、provider 不构造"同源：无组工具也不能自己起名字，否则可冒用别人来源。
2. **`solo` 是保留组名**：任何 provider 真注册一个叫 `solo` 的组 → **装载期拒载 + ERROR**。
3. **注入**：`mod:snowleopard:solo` 一节，展示名"来源名 · 无组工具"，成员全量直给；空则不占行。
4. **定位**：稳定性兜底，不是常规形态。常规情况工具必须入组（否则组清单的分层价值被稀释）。
5. **规范补充**：**尽可能不要设计无组工具；不得不设计时 `summary` + `usage` 必填**
   （组可以只给简介、详解按需查；无组工具没有组详解兜底，简介是它唯一的信息源）。
6. **跨来源不合并**：A 模组与 B 模组的散件是两个 `solo` 组——散件最容易重名（`status`/`query`），按来源分才不会撞。

## 七、规范条款与校验方式（都进 check）

| # | 条款 | 校验位置 |
| --- | --- | --- |
| 1 | **组详解必须带完整目录**：功能一句话 + 逐条列出全部成员路径 + 使用要点 | core 注册表校验：`details` 非空，且 **`tools` 里每个名字都出现在 `details` 中**；违规记 **WARN**（不拒载，避免框架 13 组未补时直接构建红），由各仓 check 做**硬断言** |
| 2 | 无组工具必须带 `summary` + `usage` | core 装载期：`solo` 工具缺任一即**拒载**（组允许无详解，无组工具不允许无简介） |
| 3 | `tool_help` 的**用法本身**要注入提示词 | core `injectionBlock()` 断言含 `tool_help`/`tool_scope` 与"下一轮可用"语义 |

**为什么"完整目录"是硬要求**（15:07 裁决理由）：目录是模型**确认工具路径**的唯一依据。
只写"这组管移动，有移动/跳跃/寻路"，模型知道"移动类"存在，却拼不出 `move.goto` 这个可调用路径，
只能猜名字（`goto`？`navigate`？）或放弃这组——**效果等于没查**。

推荐 `details` 三段模板（模板固定，方便 check 与人工校对）：

```
功能：一句话说清这组解决什么问题（≤30 字）
目录：
- move.move(direction?, distance?, ...) — 三驱动移动（相对方向/绝对距离）
- move.goto(x,y,z) — 寻路到目标点
- move.status() — 查进度与阻塞
使用要点：三驱动互斥；DONE=连续 2 tick 贴住目标；阻塞=单 tick 水平位移 <0.02×12
```

**工作量实测**（本轮已核对源码）：
- **6 个内置组**：`details` 里**已经包含了全部成员工具名**（散文式，如"session_yield 主动收束…"），
  目录完整性断言**能过**，但不符合三段模板（缺签名与分组目录）→ 改写成模板，属 core 侧轻活（C1 顺带）。
- **13 个实体组**：`details` 全是同一个占位串"实体控制工具组（雪豹框架 entitytools）——详情随里程碑逐步充实"，
  **一条成员都没有** → 必须按模板重写，这是内容工作的主体（框架侧 P1）。

## 八、风险清单

| # | 风险 | 表现 | 怎么发现 |
| --- | --- | --- | --- |
| R1 | 组简介太笼统（"实体控制工具组"） | 模型不知道能否解决当前问题 → 永不取用 | 断言：每组 `details` 含全部成员名 + 首行 ≤30 字 |
| R2 | `tool_help` 没把组加入工作集 | 查了却调不了（"可用但不可调"） | 断言：help 后下一轮 `tools` 含该组工具 |
| R3 | 每轮重算 `tools` 丢了工作集 | 上轮能用这轮说没有 | 断言：连续两轮调同组工具 |
| R4 | 拿 `isEnabled`（权限）当工作集 | 权限被会话污染、跨模型串味 | 断言：pin 前后 `isEnabled` 不变 |
| R5 | 只增不减 → 长会话膨胀回 82 个 | 又变回平铺 | 断言：`remove` 后下一轮不含；日志打"本轮工作集组/工具数" |
