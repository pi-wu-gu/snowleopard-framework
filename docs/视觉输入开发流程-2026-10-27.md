> 时间：2026-10-27 05:35 (UTC+8)　｜　前置：`docs/视觉输入可行性分析-2026-10-27.md`（设计已定稿）
> 基线：v1.12.3，真机 **23 PASS / 0 FAIL**；本线目标 **v1.13.0**
> 总体量：**7–10 天**（6 个阶段，每阶段有独立闸口与回滚点）

## 零、本流程要解决的核心问题：**降级必须可得知**

用户点名的这条，是整条线的**设计约束**而不是收尾补充。它决定了为什么 P0、P1 排在渲染之前。

现在的风险很具体：如果 provider 从 VLM 故障转移到纯文本模型、或者没有客户端能渲染，
**模型什么都不知道**，却会照常说"我看到前面是石墙"。这就是「假成功」的变种——
比失败更坏，因为下游决策全建在幻觉上。

所以先立规矩：**模型在任何时刻都必须知道"我现在能不能看图、看到的是不是真的"**。

---

## 一、四级能力模型（L0–L3）

| 级 | 条件 | 模型能拿到什么 | 允许的说法 |
| --- | --- | --- | --- |
| **L0** | VLM 可用 ∧ 客户端可渲染 | 真截图（进上下文） | "我看到…" |
| **L1** | **VLM 不可用**（provider 降级到文本）∧ 客户端可渲染 | 图落盘 + 文字描述 | **不许**说"我看到"，只能说"系统提示画面上有…（我无法查看图像）" |
| **L2** | VLM 可用 ∧ **无客户端/区块未加载** | 只有 `vision/scan` 的射线描述 | 不许说"截图里"，只能说"按视线射线推断" |
| **L3** | 两者都不可用 | 只有射线描述 | 同上 |

**降级链是动态的**：同一会话内，第一次调用可能 L0，第二次可能因为 provider 挂了变 L1。
所以"能力"不是会话常量，**每次工具结果都要重新报**。

### 1.1 四个可见面（缺一个就有盲区）

| # | 面 | 位置 | 内容 | 为什么必须有 |
| --- | --- | --- | --- | --- |
| 1 | **系统提示词** | `AiHost.systemPrompt` | 一行：`视觉能力：L2（无客户端可渲染）——你没有看图能力，不要声称看到了画面；需要空间信息请用 vision/scan` | 会话开头就定调，避免它先入为主 |
| 2 | **工具结果字段** | 每个 vision 工具返回 | `{"capability":"L1","provider":"deepseek(降级)","delivery":"text-only","reason":"VLM 不可用"}` | 每次调用都能自查 |
| 3 | **状态查询** | 扩展已有的 `view/status` | 新增 `vision` 块：能力级、当前 provider、是否 multimodal、待投递图数、最近一次失败原因 | **不新增工具**（工具数保持 47），模型可随时问 |
| 4 | **降级发生时的下一轮** | `converse` 装配阶段（单一注入点） | 一行警示：`注意：本会话已降到 L1（视觉模型不可用）——之前的图我看不了，只有文字描述` | 抓手是"状态变了要说" |

**面 2 是硬要求**：`delivery` 字段必须区分 `image` / `text-only` / `raycast`。
模型看到 `text-only` 就知道自己没图，不会编。

### 1.2 禁止话术（写进系统提示词）

> L1/L2/L3 下：**不得使用"我看到/图上显示/画面里"这类表述**；只能写"按视线射线，正前方 5 格是…"。

理由：这不是礼貌问题，是**幻觉的入口**。一旦它说"我看到"，后续推理会把这个虚构事实当既定条件。

### 1.3 测试桩也必须标出来

P3 阶段会用 `stub` 渲染后端（无客户端也能跑通管线）。此时能力级仍是 L0，但图是**假的**：

- 结果里带 `source: stub`；
- 文案带 `（测试桩，非真实画面）`；
- **只在 clienttest 模式可用**，生产配置校验拒绝 `backend=stub`。

否则测试桩会成为最隐蔽的"假画面"。

## 二、五条闸口规则（不通过就不许进下一阶段）

1. **每阶段必须有不依赖客户端的验收手段**——否则渲染一卡，整条线停摆、无法定位问题。
2. **每阶段收尾必跑真机 23 条基线**，一条不许回退（新增断言只增不改）。
3. **每阶段收尾必须文档记账**（升版本 + `开发流程-2026-10-23.md` 追加），
   `DocsCheckTest` 的版本链断言会当场拦"发版不记账"。
4. **每阶段可单独 revert**：一个阶段一个 commit + tag，配置开关能关掉本阶段能力。
5. **数字类断言单列**：`12→13` 组、`44→47` 工具——这类漂移检查器查不出来，必须写死断言。

## 三、阶段划分

### P0　配置与角色路由（1–1.5 天）— 关键路径起点

**目标**：让"按用途选 provider"成立，且带图请求不可能落到文本模型。

| 产出 | 文件 |
| --- | --- |
| `Provider.multimodal` + `vision_model`，`roles{chat,vision,compress}`，`vision{}` 段 | `host/LlmConfig.java` |
| `chat(modelId, messages, tools, requiresVision)` 能力守卫；`complete(role, …)` | `host/LlmClient.java` |
| `textOf(Object content)` 归一化（数组式 content） | `host/LlmClient.java` 或 `AiHost` |
| `compressorOrNull` 传 `role=compress` | `host/AiHost.java` |

**闸口**
- 带图请求在 VLM 必失败时 → 抛"无可用视觉 provider"，**日志里不得出现请求落到文本 provider**；
- 记忆压缩请求体的 `model` == `roles.compress` 那家，**不是** VLM；
- 摘掉 `roles` 配置时行为与 v1.12.3 完全一致（向后兼容）。

**回滚点**：`git revert` 本 commit；`roles` 缺省即旧行为。

---

### P1　能力分级与"降级可得知"（0.5–1 天）— 用户点名项

**目标**：L0–L3 在四个可见面全部落地。

| 产出 | 文件 |
| --- | --- |
| `VisionCapability`（算级 + 原因），单点实现 | `host/VisionCapability.java`（新） |
| 系统提示词追加一行能力声明 | `AiHost.systemPrompt` |
| `view/status` 返回加 `vision` 块 | `EntityToolsModule` + `ToolSchemas`（只改描述，不加工具） |
| 降级变更检测 + 下一轮注入警示 | `AiHost.converse`（单一注入点） |

**闸口**
- 关掉 VLM（`multimodal=false`）→ 系统提示词含 `L1`、工具结果含 `delivery: text-only`；
- 会话中途摘掉 VLM → 下一轮 user 消息出现降级警示**一次**（不重复刷）；
- `view/status` 的 `vision` 块字段齐全；**工具数仍为 47、组仍为 13**。

**回滚点**：能力块整体由 `vision.enabled` 控制，关掉即恢复原提示词。

---

### P2　`vision/scan`（B 档，1 天）

**目标**：无客户端也能给出真实空间信息；顺便**跑通从工具到注入的整条链路**。

| 产出 | 文件 |
| --- | --- |
| 射线（`ClipContext.Block.VISUAL` + `MapColor.col`）+ 文字摘要 + 可选小图 | `entitytools/.../mc/VisionTools.java`（新） |
| 手写 PNG 编码（`Deflater`，零依赖） | `entitytools/.../tools/PngWriter.java`（新） |
| `GroupNames.VISION` + 3 个 schema | `tools/GroupNames.java`、`ToolSchemas.java` |
| `Ctx.vision()` 默认方法（**契约在工具层、实现由壳注入**，同 `PickupCarrier` 先例） | `EntityToolsModule.Ctx` |

**闸口**
- 正前方 5 格 3×3 红羊毛 → 中心命中 `red_wool` 且距离 5±0.5；
- `view/look` 转 180° → **不再命中**（单向断言抓不到"方向反了"）；
- 结果带 `source: raycast`；PNG 前 8 字节与 IHDR 宽高正确；
- 射线开销：64×36 下 < 30 ms（服务端主线程，超了就降分辨率）。

**回滚点**：`vision.enabled=false` → 三个工具不注册（工具面回落 44）。

---

### P3　异步管线 + 假渲染器（1.5–2 天）— **去风险的核心**

**目标**：把"受理 → 回执 → 注入 → 冲突"整条链路跑通，**完全不碰客户端渲染**。

用 `VisionBackend` 接口 + `StubVisionBackend`（服务端生成一张带网格和"STUB"字的 PNG），
让 P3 的验收与渲染能力**彻底解耦**。

| 产出 | 文件 |
| --- | --- |
| `VisionBackend` 契约（request/cancel/status） | `entitytools/.../tools/VisionBackend.java`（新） |
| `PendingStore`：reqId、状态机、超时、DEFERRED、上限、落盘 | `host/VisionPending.java`（新） |
| `StubVisionBackend`（仅 clienttest） | `host/StubVisionBackend.java`（新） |
| 注入点接线 | `AiHost.converse` 装配阶段 |
| `vision/show`（重看已落盘图） | `VisionTools` + `pending` 目录 |

**闸口**
- 工具往返 < 50 ms 且返回 `reqId`（没偷偷同步）；
- 假图注入成功 ∧ **`history.jsonl` 不含 `base64`/`data:image`** ∧ `MemoryRecorder` 无 data URI；
- 客户端"不回" → 2 s 后注入失败提示，模型能继续；
- 连发两次 → 第二次 `Warn`；会话进行中回图 → `DEFERRED` ∧ 下次会话带"延迟 Xs"；
- 未投递 ≥2 → 只注入最新并说明丢弃旧图；
- `vision/show` 重看**不新增 reqId、不耗 GPU**。

**回滚点**：`vision.backend=stub` 与真实现并存；P3 完全可独立发布。

---

### P4　真渲染：网络包 + 客户端离屏（2.5–3.5 天）— 唯一不确定项

**目标**：`VisionBackend` 换成真实现（服务端发包 → 客户端离屏渲染 → 回执）。

| 产出 | 文件 |
| --- | --- |
| 2 个 payload（请求/回执）+ 注册 | `client/vision/VisionPayloads.java`（新） |
| 客户端离屏渲染（RenderTarget + Camera 替换 + `renderLevel` + `takeScreenshot` + ImageIO） | `client/vision/PovRenderer.java`（新，**独立类**） |
| 客户端选取（同维度、区块已加载、最近优先） | `host/ClientVisionBackend.java`（新） |
| 分辨率协商（值随请求下发，回执带实际宽高） | 同上传 |

**闸口**
- 无合格客户端 / 载体离所有玩家 300 格 → `Error` ∧ 文案含 `vision/scan` ∧ **无 reqId**；
- 真图尺寸 == 请求尺寸；PNG 头正确；回执宽高不符 → 作废；
- 两个客户端同时回执 → 只认先到，另一个 `Warn`；
- **渲染失败不许崩客户端**：try/catch + 回执带失败原因，服务端注入失败提示；
- 真机肉眼验收网格（朝向/贴地/大小/远景/近景/下雨/水下各一张）。

**回滚点**：`vision.backend` 切回 `stub` 或直接 `enabled=false`——**P0–P3 能力不受影响**。

## 五、关键路径与并行度

```
P0 ──► P1 ──► P2 ──► P3 ──► P4 ──► P5
        │              ▲
        └── P2 可与 P3 交换顺序（互不改同一文件）
```

- **P0 是唯一硬前置**：所有后续都依赖 `requiresVision` 与 `roles`。
- P2 与 P3 可交换：先 P3 也行（用 stub 出图），但先 P2 能更快拿到"真实空间信息"的反馈。
- **P4 必须在 P3 之后**，因为要用 P3 的 `VisionBackend` 契约；反过来 P4 的任何失败都不阻塞 P0–P3 交付。

## 六、不做清单（防扩散）

- ❌ 不做每轮自动截图（视觉是按需工具，不是感知流）
- ❌ 不做视频 / 多帧连拍
- ❌ 不做"回传玩家自己的画面"（那是另一个需求）
- ❌ 不在 P3 之前碰渲染代码
- ❌ 不为视觉给 `entitytools` 增加对 `shell` 的依赖（一律走 `Ctx.vision()` 注入）

## 七、最容易翻车的三处（提前立规矩）

1. **P0 的故障转移**：`chat()` 是 `(start + attempt) % size` 的全环，忘了加守卫就会静默把带图请求
   发给文本模型——**错误表现是"模型说没看到图"，而不是报错**，极难查。所以 P0 必须有断言 24。
2. **P1 的"假能力"**：能力级算错（该 L1 报成 L0）比没有能力更坏。能力级必须**单点计算**，
   不许在提示词、工具结果、status 里各算一遍（同一职责多实现必漂移）。
3. **P4 的渲染失败**：黑屏和"渲染成功但画面是虚空"长得一样。所以闸口里要**先判定区块是否加载**，
   而不是等图出来再看——**没有客户端可渲染比"渲染出空世界"好一万倍**。
