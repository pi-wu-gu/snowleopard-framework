## 二、三条硬约束（都有代码/环境证据，不是推断）

### 约束 1：AI 宿主跑在服务端进程里，手上**没有帧缓冲**

- `host/AiHost.java` 的驱动是 `ServerTickEvent` + `ServerLifecycleHooks.getCurrentServer()`，
  工具调用统一走 `server.execute + latch`（第 380–400 行），注释明写"你是运行在 Minecraft 服务器里的自主模型"。
- 验收环境是 **独立 `:shell:runServer` 进程 + 外部真实客户端**（`tools/launch-real-client.py`），
  两进程分离——服务端 JVM 里 `Minecraft` / `RenderTarget` / `NativeImage` **根本不存在**。
- 结论：**服务端想"截图"，只能自己造像素**，没法借游戏的渲染管线。

### 约束 2：当前三个 provider 全是纯文本配置

`host/LlmConfig.java` 的 `Provider` 只有 `name / base_url / api_key / model` 四个字段——
**没有任何多模态开关**；实际配置里的三个模型是 `deepseek-flash` / `mimo-v2.6-flash` /
`step-3.5-flash-2603`，都按文本对话在用（工具循环、JSON 参数解析、记忆压缩全走纯文本）。

要接图片，OpenAI 兼容协议要求消息体是**数组式 content**：

```json
{"role":"user","content":[
  {"type":"text","text":"这是你刚才看到的画面"},
  {"type":"image_url","image_url":{"url":"data:image/png;base64,..."}}
]}
```

`LlmClient.call` 里 `body.put("messages", messages)` 是**直接透传**的，所以协议层不用改；
但**必须有一个真的能读这个格式的端点**，否则模型会把它当文本里的乱码，或直接 400。
→ **先决条件是"换/加一个 VLM provider"，这属于配置决策，不是代码问题。**

### 约束 3：工具结果只能是字符串，图片进不了 tool 消息

- `AiHost.executeTool` 返回 `String`（`"Ok: " + o.data()`），塞进 `{"role":"tool","content": ...}`。
- OpenAI 协议里 **tool 角色不接受图片**，这是硬规定。

所以图片只能"跟着一条新的 user 消息走"：
工具返回文字摘要 → 宿主检测到"本次调用产生了图" → **追加一条 user 消息**携带图片。
这条路径要额外处理两件事：

1. `ConversationStore.append` 是 **append-only 写 `history.jsonl`**——base64 一张 512×288 约 200–500 KB，
   绝不能进历史（而且 history 本身已有"只增不减"的已知问题）。
2. `MemoryRecorder` 会把 user 消息截到 400 字符，data URI 被截断会变成垃圾进天档——必须显式跳过。

## 三、A 档：视线射线文字描述（初版判断"先做"；现已并入 `vision/scan` 的 `detail=text`）

### 设计

```
veil  = 载体眼位 entity.getEyePosition(1.0f)
dir   = entity.getViewVector(1.0f)      // 已由 view/look 驱动（EntityToolsModule:313-314 setYRot/setXRot）
```

在视锥内取 **9×5 = 45 条射线**（粗采即可描述"哪里有什么"），每条：

```java
BlockHitResult hit = level.clip(new ClipContext(eye, eye.add(dir_i.scale(range)),
        ClipContext.Block.VISUAL, ClipContext.Fluid.NONE, self));
```

- 命中：`level.getBlockState(hit.getBlockPos())` → 方块 id + 距离 + **屏幕方位**（左/中/右 × 上/平/下）
  + 命中面（顶面/侧面）。
- 未命中：记"空气/天空"，并报该方向的可视距离上限。
- 实体：`level.getEntities(self, aabb)` 里按"视线夹角 < 半 FOV 且无遮挡优先"挑最近的 2–3 个。

输出形如（喂给模型的是这段文字，不是原始 45 行）：

```
视线中心(5.2格): minecraft:red_wool [顶面]
左侧±22° : minecraft:stone_bricks @3.1格
右侧±22° : 空气（8格内无遮挡）
上方±18° : minecraft:oak_planks @4.0格（头顶）
近处实体: snowleopard:avatar "小白" @6.3格，方位左偏12°，视线未被遮挡
```

### 为什么这不是重复建设

现有工具已经给了**"有什么"**和**"往哪看"**：

- `world/query`：区域检索（中心/框选 + 方块 + 实体）
- `view/look` / `view/look_at`：设朝向、锁目标
- `sense/*`：绑定感官

它们给不出的是**"沿视线方向的遮挡关系、谁挡住了谁、我正对着什么、多远"**——
这正是 A 档补的那块。实测价值点：模型抱怨过"slimeball 走过去也没被捡"这类**"我以为在那里"**
的认知错误，视线剖面直接消灭这一类。

### 与坐标/朝向铁律的一致性

射线用 `entity.getViewVector()`，与 `view/look` 同源（它 set 的就是 `yRot/xRot`），
不会出现"看着东边、射线往西"的分家。真机断言要**双向**验：

- 正前方 5 格放 3×3 红羊毛 → 断言中心命中 `red_wool` 且距离 5±0.5
- `view/look` 转 180° → 断言中心**不再**是羊毛（这条能抓"方向反了"，单侧断言抓不到）

## 四、B 档：射线彩色小图（纯服务端出 PNG）

### 为什么可行

服务端有方块状态与**材质代表色**，不需要贴图：

```java
MapColor mc = state.getMapColor(level, pos);   // BlockBehaviour.BlockStateBase:633
int rgb = mc.col;                              // MapColor.col 是 0xRRGGBB 的 int（:69）
```

`MapColor` 是原版"地图上的颜色"，本身就是为"远看像不像"设计的，正好适配低分辨率。

### 参数与成本（这是关键拐点）

| 分辨率 | 射线数 | 32 格 DDA 估算 | 适用 |
| --- | --- | --- | --- |
| 32×18 | 576 | 3–8 ms | 只够"有墙/没墙" |
| **64×36** | **2304** | **10–30 ms** | **推荐：轮廓可辨、单 tick 内可接受** |
| 96×54 | 5184 | 25–60 ms | 会咬到 50ms tick 预算 |
| 256×144 | 36864 | 150–400 ms | 不值（真要清晰就该走 C 档） |

PNG 用 `java.util.zip.Deflater` 手写编码器约 40 行（项目原则：零第三方依赖），
64×36 RGB 原始 6.9 KB，压缩后通常 **1–3 KB**，base64 后 2–4 KB——传输与 token 都可忽略。

实体：把 `getEntities` 结果的包围盒投影到同一套相机基上，画**纯色剪影**（例如 `#C04040`），
足够表达"那儿站着个东西"。

### 一个额外收益：图可以给人看

把 PNG 落到 `ids/<模型>/vision/cap-<时间戳>.png`（家目录内，不跨 ID），
即使模型吃不下图，**玩家能直接看到"它以为它看到什么"**——这在调试视觉链路时价值极高，
也顺带让"射线渲染对不对"可被人眼验收。

## 五、C 档：载体 POV 真截图（初版判断"暂缓"；**已裁决为做**，见 §十一 起）

### 需要新建的三块基础设施

1. **自定义网络包**：全仓现在**零** `CustomPacketPayload` / `RegisterPayloadHandlersEvent` /
   `PacketDistributor`（grep 全仓为空）。C 档至少要 1 组请求/响应包 + 超时与"客户端没装/没连"的分支。
2. **客户端离屏渲染**：`Screenshot.takeScreenshot(RenderTarget)` 本身**接受任意 RenderTarget**
   （`net/minecraft/client/Screenshot.java:92`，内部 `NativeImage.downloadTexture` + `flipY`），
   所以"读一张离屏图"这步是现成的；**难的是先生成那张图**——要新建 RenderTarget、
   把相机放到载体眼位与朝向、跑一遍 `LevelRenderer` 的实体/方块图层、再恢复状态。
   这是"安全摄像头"类模组的经典做法，属于**版本敏感代码**（渲染管线每次大版本都动）。
3. **线程模型**：渲染必须在渲染线程；工具调用现在卡在 `server.execute + latch` 上。
   在服务端主线程里等一个网络往返是**明确禁止**的（会卡 tick）。要么把等待挪到宿主线程、
   在渲染线程回调后完成 latch，要么整体改成异步工具——这是对现有"工具=同步返回字符串"契约的改造。

### 还有一个绕不开的产品问题

`Screenshot.takeScreenshot(mc.getMainRenderTarget())` 抓到的是**玩家视角**，不是载体视角。
如果只想要"你看到什么"，这一条很便宜（~20 行）；但用户要的是"**载体自身视角**"，
那就必须上面第 2 步的完整离屏渲染。

### 与 B 档的比较

B 档给的是"抽象彩色图"（材质代表色 + 剪影，无光影无贴图细节），
C 档给的是"真画面"。对模型来说，**低分辨率真图未必比 64×36 的抽象图更有信息量**——
而 C 档贵 5–10 倍且带版本脆弱性。所以顺序应该是"先用 B 验证视觉链路是否真的有收益，
再决定要不要上 C"。

## 六、接线设计（初版：同步形态；**已被 §十二–§十七、§二十四 取代**）

### 工具面

**初版建议**挂在现有 `view` 组，不新增组：`view/capture`（12 组 44 → 45 工具）。
**已被推翻**：裁决后改成新开 `vision` 组、3 个工具（13 组 47，见 §二十四）——因为需要
异步受理（不是一次性返回）、重看已落盘图（`show`）、保留纯服务端射线档（`scan`），
三件事塞进 `view` 会把 `look/look_at` 的语义边界搅浑。

以下参数与权限标注仍然有效（完整的配置清单见 §二十三）：

| 参数 | 默认 | 说明 |
| --- | --- | --- |
| `range` | 32 | 射线最大距离（夹取 4..64） |
| `detail` | `text` | `text` / `image` / `both` |
| `w`/`h` | 现为配置项（默认 384×216） | 初版写死 64×36；裁决后改为可配置，夹取 64..640 / 36..360（§十八） |

返回（文字部分）：中心命中 + 四向分布 + 近处实体 + 图路径（若出图）。
权限标 `reversible: true`、**不写 `changes_world`**（只读，不该触发审批）。

### 送图进模型（初版：只加一个布尔；**不够**，见 §十七）

1. `LlmConfig.Provider` 加一个布尔 `multimodal`（默认 false）。
   **初版遗漏**：仅此不够——还需 `roles{}` 角色路由（否则记忆压缩被带偏）与
   `requiresVision` 能力守卫（否则故障转移把带图请求甩给文本模型），见 §十七。
2. `AiHost` 在工具返回后检查"本次是否产图 ∧ 当前 provider.multimodal"：
   是 → 追加一条 user 消息（text + image_url，base64 data URI）；
   否 → 只发文字，并在文字里加一句"（本模型不支持看图，已给出文字描述）"——**不能让模型以为自己在看图**。
3. 这条消息**不写 `history.jsonl`**、**不进 `MemoryRecorder`**，只在当轮 messages 里存在。

### 预算护栏（必须有）

- 每会话最多 `N` 次出图（默认 2），超出返回 `Warn`（"本轮视觉预算已用完"）。
- **不做每轮自动截图**：一次 10–30 ms 服务端 + 每轮几百 token，长期跑就是纯烧钱。
  视觉是**按需工具**，不是被动感知流。

## 七、可断言性（能进真机自测，且能抓真 bug）

自测房间里做（封闭空间、坐标锚定世界常数，避开高度图）：

| 断言 | 判据 | 抓什么 |
| --- | --- | --- |
| 视线中心命中 | 正前方 5 格 3×3 红羊毛 → `red_wool` ∧ 距离 5±0.5 | 射线方向/起点 |
| 反向不命中 | `view/look` 转 180° → 中心**不是**羊毛 | **方向反了**（单向断言抓不到） |
| 遮挡优先级 | 羊毛前 2 格立石墙 → 报 `stone` 而非 `red_wool` | 是否真的取最近命中 |
| PNG 结构 | 前 8 字节 `\x89PNG\r\n\x1a\n` ∧ IHDR 宽高 == 请求值 | 编码器 |
| 图的颜色语义 | 中心 5×5 像素 R > G 且 R > B（红羊毛） | 颜色映射错位 |
| 预算护栏 | 同轮第 3 次调用 → `Warn` | 护栏生效 |
| 不吃图的分支 | provider 未声明多模态 → 返回文字且**不含** data URI | 把 base64 当文字塞进上下文 |

最后一条特别重要：**"模型吃不下图却被塞了 base64"**会造成隐性 token 爆炸 + 模型胡言乱语，
这是最容易上线才发现的问题。

## 八、风险清单

| 风险 | 影响 | 对策 |
| --- | --- | --- |
| 服务端主线程开销 | 2304 射线 10–30 ms，接近 tick 预算的 1/2 | 默认 64×36；`range` 上限 64；不自动调用 |

# 第二轮设计（2026-10-27 05:20 (UTC+8)）：直接上 C 档 + 异步结果注入

用户裁决：**① 直接做 C 档（载体 POV 真截图）；② 同时给模型"查看截图"的能力；
③ 图片工具异步——发起申请即返回、会话继续跑、结果稍后注入（图或失败提示）；
④ 必须处理多次唤起冲突并给出提示。**

这一版把"能不能画"推进到"异步管线怎么搭、冲突怎么裁决"。下面是按现有代码逐条落地的设计。

## 十一、结论

**可行，但它不是一个"工具"，而是一条跨进程的异步管线。** 需要新建四块基础设施，
其中两块（网络包、客户端离屏渲染）在全仓是**零起点**。

| 项 | 现值 | 目标 |
| --- | --- | --- |
| 工具语义 | 同步：`dispatchOnServer` + latch，返回字符串 | 异步：**受理即返回 reqId**，结果走注入 |
| 客户端能力 | 服务端 JVM 无 `Minecraft` | 新增客户端渲染模块 |
| 通信 | **全仓零自定义 payload** | 2 个 payload（请求/回执） |
| 结果通道 | 只能进 tool 消息（不能带图） | 图片作为**新的 user 消息**注入 |
| 模型侧 | 三个 provider 全是文本（无多模态字段） | 加 `multimodal` provider + `roles{}` 角色路由（§十七） |
| 工具面 | 12 组 44 工具 | **13 组 47 工具**（`vision/{capture,scan,show}`，§二十四） |
| 分辨率 | —（写死 64×36 的射线图） | **配置项**，默认 384×216，随请求下发（§十八） |

关键结论一句话：**异步不是为了省时间，是为了不把"一次 GPU 渲染 + 一个网络往返"塞进
"服务端主线程 + 工具同步契约"里。** 同步做 C 档必然要在服务端主线程等客户端，
那是明确禁止的（会卡 tick）；异步是唯一正确的形态。

## 十二、四块基础设施

### 12.1 客户端离屏渲染（核心难点，版本敏感）

已核实的可用 API（1.21.1 / NeoForge 21.1.259）：

| 用途 | API | 证据 |
| --- | --- | --- |
| 建离屏缓冲 | `com.mojang.blaze3d.pipeline.RenderTarget(boolean useDepth)` + `resize` + `bindWrite` + `clear` | `RenderTarget.java:34/186/250` |
| 摆相机 | `Camera.setup(BlockGetter, Entity, boolean, boolean, float)` + `setRotation(yRot, xRot, roll)` + `setPosition(Vec3)` | `Camera.java:47/56/57` |
| 画一帧 | `LevelRenderer.renderLevel(DeltaTracker, boolean, Camera, GameRenderer, LightTexture, Matrix4f frustum, Matrix4f proj)` — **public** | `LevelRenderer.java:921-923` |
| 读像素 | `Screenshot.takeScreenshot(RenderTarget)` → `NativeImage`（内部 `downloadTexture` + `flipY`） | `Screenshot.java:92-100` |
| 编码 PNG | `ImageIO.write(BufferedImage, "png", …)`（JDK，客户端有）；vanilla 自己也是 `NativeImage.writeToFile` | `Screenshot.java:76` |

**流程**：在客户端渲染线程上——按**请求下发的宽高**建 RenderTarget（不读本地配置）→
备份并替换相机（位置=载体眼位，
朝向=**服务端下发的 yaw/pitch**，不信任客户端同步值）→ 设 projection/frustum → `renderLevel` →
`takeScreenshot` → 还原相机与主帧缓冲 → 编 PNG → 回执。

**风险**：`renderLevel` 是"整帧渲染"的入口，调用它需要堆好 `RenderSystem` 的
modelview/projection、雾、光照贴图等前置状态；漏一项就是黑屏或者崩。
这是**每次大版本都可能坏**的代码，必须隔离成单独类（`client/vision/PovRenderer`），
失败时**降级**而不是崩客户端。

### 12.2 网络包（两个方向，复用 NeoForge 标准 API）

```java
// mod 总线
event.registrar("1")
     .executesOn(HandlerThread.MAIN)
     .registerBidirectional(VisionRequest.class, VisionRequest.STREAM_CODEC, VisionRequest::handle)…
```

`PayloadRegistrar` 支持 `registerToClient / registerToServer / registerBidirectional`、
`executesOn(HandlerThread.MAIN)`（自动包成 `MainThreadPayloadHandler`）；
`IPayloadContext` 提供 `player()` 与 `enqueueWork(...)`；
发包用 `PacketDistributor.sendToPlayer(ServerPlayer, payload)` / `sendToServer(payload)`。

**体积上限已核实**：`ClientboundCustomPayloadPacket.MAX_PAYLOAD_SIZE = 1048576`（1 MiB）。
384×216 的 PNG 约 80–200 KB，安全；512×288 约 200–500 KB，也能过但余量小。
**建议 384×216**，并按"载体内存里最多 2 张未投递图"的上限兜住。

### 12.3 谁来回图（渲染客户端的选取）

载体不是玩家，服务端要指定一个客户端干这活。规则：

1. 候选 = 与载体**同维度**、且**区块已加载**的玩家（§十三）；
2. 取**距离载体最近**的一个；同距离取先加入的（确定性）；
3. 没有候选 → **受理阶段直接失败**：不放 reqId、不让模型白等，且文案里点名 `vision/scan`；
4. 多个客户端同时回图 → **只认第一个到达的**，其余回 `Warn: 重复回执（已作废）`。

### 12.4 线程模型

```
服务端主线程（工具受理）   → 立刻返回 reqId，不阻塞
服务端主线程               → PacketDistributor 发给选中客户端
客户端 MAIN（渲染线程）    → 离屏渲染 + 编 PNG（约 20–60 ms）
客户端 NETWORK             → 回执 payload
服务端 MAIN                 → 落盘 ids/<id>/vision/cap-*.png + 写 pending 记录
宿主线程                    → 尝试唤醒（见 §十五）
```

**任何一步都不在服务端主线程上等待**。这是设计红线。

## 十三、C 档有一条 B 档没有的硬限制：客户端只能渲染它已加载的区块

这是本轮最重要的发现，直接决定"能不能用"：

- 客户端的世界数据来自服务端推送的 chunk。载体跑到离**所有玩家**超过视距（默认 8–10 区块）
  的地方，客户端**根本没有那片地形**——渲染出来会是虚空 + 天空。
- 不是"画质差"，是**画面是假的**：模型会看到"前方一片空"，然后做出错误决策。

所以：

| 条件 | C 档 | B 档（服务端射线） |
| --- | --- | --- |
| 有玩家在载体附近（≤8 区块） | ✔ 真实画面 | ✔ |
| 载体独自在远处 | ✘ **无地形（假画面）** | ✔ 真实方块数据 |
| 无任何客户端在线 | ✘ | ✔ |

**结论：C 不是 B 的超集。**

**裁决修正（05:25）：不自动降级，B 档改成模型可选工具。** 初版写的是"无客户端时自动走 B 档"，
现在改为：

- `vision/scan`（B 档）作为**独立工具**暴露给模型，由模型自己决定什么时候用它；
- `vision/capture`（C 档）在受理阶段判定不可用时，**返回明确错误并带行为指引**：
  `Error: 无可渲染客户端（最近玩家 312 格外，区块未加载）——改用 vision/scan 获取视线方块描述`；
- **绝不**把射线结果伪装成截图返回。

改的理由是"假画面"的同一条逻辑往上一层：自动降级虽然保证"总有感知"，但会让模型**分不清
自己拿到的是实拍还是抽象图**——它会把 64×36 的材质代表色当成真实视觉，进而笃定"那面墙是红的"。
**宁可让模型知道自己看不了，也不要让它看错。** 这与项目既有做法一致：错误文案必须带行为指引
（12:14 `chat_send` 超长被拒后模型自愈重试，就是靠文案里的指引）。

## 十四、状态机（一次视觉申请的完整生命周期）

```
            ┌──────────── 受理阶段（同步，服务端主线程）─────────────┐
 调用 vision/capture
   ├─ 参数非法            → Error（不占 reqId）
   ├─ 本模型已有在飞请求  → Warn  「上一张仍在渲染（reqId），本次未受理」   ← 冲突①
   ├─ 无可渲染客户端      → Error + 指引「改用 vision/scan」（不降级、不伪装）  ← 冲突②
   └─ 通过                → Ok「已受理 reqId=…（约 1s 内注入）」，状态=REQUESTED
                                    │
                    ┌───────────────┴───────────────┐
             客户端回图（正常）                超时（默认 2000 ms，可配）
                    │                               │
              落盘 + pending[reqId]=READY       pending[reqId]=FAILED(超时)
                    │                               │
                    └──────────────┬────────────────┘
                                   ▼
                        尝试注入（§十五）
                    ┌──────────────┴───────────────┐
        当前无会话在跑 → 发起唤醒             已有会话在跑 / 唤醒被拒
                    │                               │
              新 turn 携带图片                 pending=DEFERRED（附原因与延迟）
                                                        │
                                              下一次会话开头捎带（单一注入点）
```

**reqId 生命期**：受理 → 回执/超时 → 注入成功。注入成功即删除 pending 记录；
**图文件保留**（供 `vision/show` 重看与人工排查），只保留最近 N 张（默认 20）。

## 十五、冲突裁决表（用户点名的"多次唤起冲突提示"）

| # | 冲突 | 判据 | 处理 | 谁看到 |
| --- | --- | --- | --- | --- |
| ① | 同模型连发两次 capture | pending 里有同模型 REQUESTED | 第二次 `Warn`，**不排队**（排队=把失败变稍后执行） | 模型（工具结果） |
| ② | 无可渲染客户端 | 无同维度玩家 ∨ 区块未加载 | `Error` 并**在文案里点名 `vision/scan`**；不降级、不产生 reqId | 模型 |
| ③ | 回图时会话正在跑 | 唤醒被 `runtime` 拒（`<id>.lock` 存在） | 挂 `DEFERRED`，**不重试**；下次会话捎带并注明"延迟 Xs" | 下次会话 |
| ④ | 多客户端同时回图 | 同 reqId 第二次回执 | 丢弃 + 回 `Warn`；**以先到者为准** | 客户端日志 |
| ⑤ | 图回来时载体已死/被解绑 | 绑定实体不存在 | 图仍落盘，`pending` 标 `ORPHAN`，注入时带一句"拍摄时载体已不存在" | 下次会话 |
| ⑥ | 注入时已有未投递图 | `READY|DEFERRED` 数量 ≥ 2 | 只注入**最新一张**，其余转 `DROPPED` 并在文字里说明"另有 N 张较早截图已丢弃" | 模型 |
| ⑦ | 玩家侧想看到冲突 | — | 聊天栏一行灰字（仅在 `feedback` 开启时，与唤醒回执同一开关） | 玩家 |

**③ 是核心**：它与核心既有裁决"唤醒失败不排队、只登记需求"一致——
**不排队去执行，但结果作为状态留着**。这样既不违反"失败不变成稍后执行"，
也不会丢图。

## 十六、结果注入：三个层次 + 单一注入点

| 层次 | 触发 | 图片位置 | 时延 |
| --- | --- | --- | --- |
| **轮内** | 图在**本轮** `converse` 循环返回前到 | 追加到本轮 messages（作为 user part） | 0 |
| **轮后唤醒** | 图在会话结束后到，且唤醒成功 | 新 turn 的第一条 user 消息 | ~1 cycle |
| **下次捎带** | 唤醒被拒 | 下次会话装配阶段拼进 user 内容 | 不定 |

**推荐实现"轮后唤醒 + 下次捎带"，不做"轮内等待"**——一旦为了等图而在 `converse` 里阻塞，
异步就退化成同步，前面所有设计都白做。

**单一注入点**：注入必须挂在 `AiHost.converse` 的①装配阶段（那里已经在拼
`user` 文本 + 记忆注入），**不许另开一处拼**。这与项目既有铁律"同一注入点统一装配
（`TURN_END` 只许 `WakeBridge.turnLine` 一处拼，谁后加谁覆盖）"同源。

**强制排除**（漏了会静默烂账）：
- 图片消息**不写** `history.jsonl`（append-only，base64 会爆，且 history 只增不减）；
- **不进** `MemoryRecorder`（400 字符截断会把 data URI 变成垃圾进天档）；
- 图片落 `ids/<id>/vision/`（家目录内，**不跨 ID**）。

## 十七、模型侧：「查看截图」的两件事

### 17.1 吃图：裁决为「加 VLM provider」

```json
{"name":"…","base_url":"…","api_key":"…","model":"…","multimodal":true,"vision_model":"可选"}
```

- `multimodal=false` 时：工具**只返回文字摘要 + 图路径**，并在文字里明说
  "本模型不支持看图，图已保存到 …（可让玩家查看）"——**不能让模型以为自己在看图**。
- `multimodal=true` 时：注入 user 消息（text part + `image_url` data URI）。
- `vision_model` 可选：让**主模型继续用文本模型、只有视觉轮切到 VLM**，
  避免为了看图把整个会话换成更贵的模型。

**序列化不用改**：`Json.write` 已支持 `Map` / `Iterable` / `null`（`Json.java:58-90`），
多模态数组式 content 与嵌套 `image_url` 都能原样输出。

#### 但加 provider 会踩到两个既有机制（这是本节最重要的部分）

**风险 A：故障转移会把"带图请求"甩给纯文本模型。**

`LlmClient.chat` 的转移是**全 provider 环**：

```java
for (int attempt = 0; attempt < config.providers().size(); attempt++) {
    LlmConfig.Provider p = config.providers().get((start + attempt) % size);
```

也就是说：视觉请求在 VLM 上失败（超时/429）→ **自动落到下一个纯文本 provider**，
把带 `image_url` 的消息发过去 → 400，或更糟：端点亮绿灯但**静默忽略图片**，
模型基于"没有图"的上下文回答，而宿主以为它看过了。

**对策**：`chat(...)` 增加 `requiresVision` 参数；带图请求**只在 `multimodal=true` 的
provider 之间转移**，全部失败则抛出明确异常（"无可用视觉 provider"），
**禁止降级到文本模型**。这条与既有铁律同源：*故障转移会掩盖上游 400/不可用*
（2026-10-24 审查抓到的"可见但不可用"就是被故障转移掩盖的）。

**风险 B：`Compressor` 会跟着 providers 顺序跑，跟视觉无关。**

`AiHost.compressorOrNull` 造出的压缩器走 `LlmClient.complete(...)`，
而 `complete` 里写死 `chat("", …)`——`modelId` 是空串，`config.models().get("")` 通常为 null，
于是 `start = 0`，**永远用 providers 列表的第一个**。

后果：如果为了视觉把 VLM 加在列表**首位**，**记忆压缩会改用 VLM**（更贵、更慢，
且 VLM 未必擅长长文本摘要）；如果把 VLM 放**末位**，视觉请求又只会在前几家全挂时才用上。

**对策**：不能靠"providers 顺序"表达用途。配置里新增显式的角色路由：

```json
"roles": { "chat": "deepseek", "vision": "qwen-vl", "compress": "deepseek" }
```

`chat()` 按 `roles[role]` 选起点；`complete()` 显式接收 `role=compress`。
**这是本轮唯一必须动既有代码结构的地方**（`LlmClient.chat` 签名 + `complete` 加参数），
其余都是新增。

**风险 C：VLM 可能返回数组式 content。**

`AiHost` 取回复用 `String.valueOf(assistant.get("content"))`。文本模型返回字符串没问题，
但部分视觉模型返回 `[{"type":"text","text":"…"}]` 数组 → 会被 `toString()` 成
`[{type=text, text=…}]` 这种垃圾进上下文。**需要一个 `textOf(Object content)` 归一化**
（string 原样、数组取各 text part 拼接、null → 空串）。

### 17.2 重看：`vision/show <cap-id>`（几乎白送）

图已落盘，这个工具**不重新渲染、不耗 GPU、零延迟**，只把旧 PNG 重新注入。
价值：模型可以"对比刚才和现在"、"回头再看一眼那个东西"，而不用再拍一张。
参数：`cap-id`（缺省=最近一张）、可选 `zoom` 建议给模型的裁剪区域（服务端裁剪需要额外编码，可后置）。

> 有了 17.2，"多拍几张"的动机大幅下降——**看图的成本变成 0，拍照的成本仍然高**，
> 这是最省钱的资源分配。

## 十八、分辨率：裁决为「可配置字段」

分辨率**不写死**，作为配置项（服务端权威），随每次渲染请求下发给客户端——
**客户端必须用请求里的值渲染**，不许读自己的本地配置，否则图尺寸与服务端记录不符（§十五 断言会红）。

| 档位 | PNG 估算 | 图 token（量级，随模型） | 用途 |
| --- | --- | --- | --- |
| 256×144 | 40–90 KB | 200–400 | 省；只够"有没有东西" |
| **384×216** | **80–200 KB** | **400–700** | **默认值** |
| 512×288 | 200–500 KB | 700–1200 | 需要看清远处/细节 |
| 640×360 | 300–800 KB | 1200–2000 | 上限附近，慎用 |

**配置约束（不做就是坑）**：

| 项 | 规则 | 理由 |
| --- | --- | --- |
| 夹取 | 宽 `64..640`、高 `36..360`，非 16:9 也接受但要提示 | 非法值直接拒，别让它算出 0 或负数 |
| 包上限 | 编码后 > 768 KB 时**自动降一档重渲**（只降一次） | `MAX_PAYLOAD_SIZE = 1048576`，留 25% 余量给其它字段 |
| 读取时机 | 每次受理时读配置（热改生效），不缓存跨会话 | 分辨率改了要能立刻试，不必重启 |
| 与客户端协商 | 值随 payload 下发；客户端**回执里带回实际宽高**，服务端校验不一致即作废 | 防止客户端旧配置/被改包 |
| token 成本 | 分辨率变大 → 图 token 线性上涨 | 预算护栏要按"像素数"而非"张数"计 |

**预算护栏**（必须有）：
- 每会话最多 `N` 次**拍摄**（默认 2，可按 token 预算折算）；`vision/show` 不计入（不耗 GPU）；
- 未投递图上限 2 张（超出按 §十五 ⑥ 丢旧）；
- 不做每轮自动截图。

| 10 | **角色路由** | 记忆压缩的请求体 `model` 字段 == `roles.compress` 那家的模型，**不是** VLM | 风险 B（压缩被带偏） |
| 11 | 分辨率 | 配置改 512×288 → 图实际尺寸 == 512×288 ∧ 回执宽高与请求一致；回执改宽高 → 作废 | §十八 协商 |
| 12 | 数组 content | 伪造 VLM 返回 `[{"type":"text","text":"看到墙"}]` → 入库是 `看到墙`，不是 `[{type=text…}]` | 风险 C |

第 8 条最容易被忽略也最坑：**假画面比没画面坏**——模型会笃定"前方是空的"。
第 9、10 条是本轮新增代码里**唯一会污染既有功能**的两处（故障转移、记忆压缩），必须单独断言。

## 二十一、风险（按优先级，含三条新裁决带来的新风险）

| 风险 | 影响 | 对策 |
| --- | --- | --- |
| **渲染前置状态不全** | 黑屏/崩客户端 | 拆独立类 + 包 try/catch + 失败**报错并指引 `vision/scan`**（不降级、不伪装）；真机先只拍"静止画面" |
| **假画面（区块未加载）** | 模型基于"空世界"决策 | §十三 受理阶段判定；**拒绝拍摄**而不是给空画面；断言 8 |
| **带图请求被故障转移甩给文本模型**（新） | 400，或端点亮绿灯但静默丢图 → 模型基于"没图"作答而宿主以为它看过 | `chat(requiresVision=true)` 只在 `multimodal` provider 间转移，全失败即抛错；断言 9 |
| **Compressor 跟着 providers 顺序跑**（新） | 加 VLM 后记忆压缩被换成贵模型，成本与质量双输 | 配置加 `roles{chat,vision,compress}`，不靠顺序；断言 10 |
| **VLM 返回数组式 content**（新） | `String.valueOf(list)` → `[{type=text…}]` 垃圾进上下文 | `textOf(content)` 归一化；断言 12 |
| **图进 history/记忆** | 磁盘爆 + 天档污染 | 硬编码排除 + 断言 3 |
| **同步退化** | 服务端卡 tick | 红线：受理阶段不等待；断言 1 守 |
| 分辨率配置非法/包超限（新） | 0 尺寸、渲染崩、发送失败 | 夹取 64..640 × 36..360；编码 > 768 KB 自动降一档；断言 11 |
| 分辨率协商不一致（新） | 图尺寸与记录不符、后续裁剪/断言失效 | 值随 payload 下发 + 回执校验宽高 |
| 两档结果混池（新） | 模型分不清"实拍"与"射线抽象图" | 注入文案与记录都带 `source: pov \| raycast`，**永不混称"截图"** |
| 渲染管线版本敏感 | 升级即坏 | 隔离类 + 失败即报错；把它当"可选能力"而非核心 |
| 多客户端争抢 | 图错乱 | 只认第一个回执；§十五 ④ |
| VLM 未配置 | 图白拍 | `multimodal` 显式声明；未声明只发文字并明说；**不静默塞图** |

## 二十二、三条裁决的落实情况

| # | 裁决 | 落地形式 |
| --- | --- | --- |
| 1 | **加 VLM provider** | `Provider.multimodal` + 可选 `vision_model` + `roles{chat,vision,compress}`，并给 `LlmClient.chat` 加 `requiresVision` 能力守卫 |
| 2 | **分辨率可配置** | 服务端权威配置，随请求下发；夹取 + 包上限自动降档 + 回执校验（§十八） |
| 3 | **B 档设为模型可选工具** | 独立工具 `vision/scan`（`detail=text\|image`）；C 档不可用时**报错并点名它**，不自动降级（§十三） |

| 字段 | 默认 | 校验/夹取 | 备注 |
| --- | --- | --- | --- |
| `roles.chat/vision/compress` | 各自回落到 providers[0] | 名字必须存在，否则启动即报错 | 不写就退回旧行为（顺序） |
| `vision.enabled` | `false` | — | 关闭时三个工具**不注册**（工具面回落 44） |
| `vision.width/height` | 384×216 | 64..640 / 36..360 | 高度可非 16:9 |
| `vision.timeout_ms` | 2000 | 500..10000 | 超时 → 注入失败提示 |
| `vision.max_captures_per_session` | 2 | 0..8 | 0 = 只允许 `vision/scan` |
| `vision.max_pending` | 2 | 1..4 | 超出丢旧（§十五 ⑥） |
| `vision.keep_images` | 20 | 1..200 | 落盘保留张数（`vision/show` 用） |
