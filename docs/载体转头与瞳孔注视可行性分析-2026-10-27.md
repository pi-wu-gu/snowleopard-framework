# 载体转头与瞳孔注视 · 可行性分析（2026-10-27 18:00 (UTC+8)）

> 命题（用户原话）："给载体加上转头和瞳孔移动，绑定指向到查看类工具查看的位置，或者锁定的生物，
> 限制转头和瞳孔移动幅度，抵达上限但仍未到就轻微移动身体朝向。"
>
> 对象：snowleopard-framework 1.13.3（内嵌 core 0.6.1）· 载体 `snowleopard:avatar`

---

## 一、结论

**可行，中低风险，1.5–2 天。** 拆成四件事，其中三件是"接线 + 加同步字段"，一件（截图视角）需要先定口径。

| 要做的 | 现状 | 难度 |
| --- | --- | --- |
| ① 头部朝向跟随注视目标 | 模型**已经**支持 `head.yRot/xRot`，但输入恒为 0（见 §二.2） | 低 |
| ② 瞳孔随残余角偏移 | 模型已有 `±0.2px` 偏移，同样输入恒为 0 | 低 |
| ③ 转头限幅（超限才转身体） | 现在是**整体瞬间转身体**，没有"头"这一级 | 中（要改锁定施加方式） |
| ④ 截图视角与视线一致 | 相机取的是**身体** yaw/pitch | **中（口径问题，见 §四）** |

最关键的一句：**③ 会把"身体朝向"和"视线朝向"拆成两个量**，而 `vision_shot` 的相机只认身体。
不先把 ④ 定下来，就会出现"模型说在看它、拍出来却是旁边"的自相矛盾。

## 二、现状盘点（都有代码位置）

### 2.1 模型侧：能力齐了，输入是死的

`client/model/SnowLeopardModel.java#setupAnim`（:289）已经写了：

```java
this.head.yRot = netHeadYaw * (π/180);          // 头左右
this.head.xRot = headPitch * (π/180);           // 头俯仰
...
float gazeX = Mth.clamp(netHeadYaw * 0.008F, -0.2F, 0.2F);   // 瞳孔
float gazeY = Mth.clamp(headPitch * 0.006F, -0.15F, 0.15F);
this.eyePupilLeft.resetPose(); this.eyePupilLeft.x += gazeX; ...  // 必须先 resetPose（v1.12.2 的教训）
```

`netHeadYaw` / `headPitch` 由 `LivingEntityRenderer` 传入 = `yHeadRot - yBodyRot`。

### 2.2 锁定侧：整体转身体，所以头永远是正的

`mc/EntityToolsModule.java#tickViewLock`（:566-582）：算出 `aim` 后直接

```java
setRotation(self, aim.yaw(), aim.pitch());   // body yaw = 目标方向
```

→ `yHeadRot ≈ yBodyRot` → `netHeadYaw ≈ 0` → **头不转、瞳孔居中**。
这正是"看起来像机器人"的原因：不是模型不会动，是**上游把差值喂成了 0**。

### 2.3 同步面：一个自定义字段都没有

`AvatarEntity extends PathfinderMob`，只有 `boundModel` 一个普通字段，
**没有 `defineSynchedData` / `SynchedEntityData`**。
所以"服务端算出的注视角度"目前**没有任何通道**能到客户端——这是必须补的一环。

### 2.4 截图：相机跟的是身体

`client/vision/PovCapture.java`（:66）用 `mc.setCameraEntity(e)` 抓帧，相机取 `e.yRot / e.xRot`。
头领先身体之后，照片会**落后于视线**。

## 三、设计

### 3.1 共享常量与纯函数（可单测）

新增 `entitytools/.../tools/AvatarGaze.java`（纯 Java，无 MC 类）：

```java
public static final double HEAD_YAW_LIMIT = 65;    // 头相对身体的最大偏航（度）
public static final double HEAD_PITCH_LIMIT = 35;  // 头最大俯仰
public static final double BODY_TURN_PER_TICK = 6; // 超限后身体追的速度（120°/s）
public static final double PUPIL_MAX_PX = 0.2;     // 瞳孔偏移上限（眼白宽 2px，物理极限 ±0.5）

public static double clampHeadYaw(double delta)      // ±65
public static double clampHeadPitch(double pitch)    // ±35
public static double bodyStep(double bodyYaw, double targetYaw)  // 朝目标最多转 6°
public static double pupilX(double residualYaw)      // residual × 0.008，夹 ±0.2
public static double pupilY(double residualPitch)    // × 0.006，夹 ±0.15
```

**为什么放共享类**：这套限位必须服务端（决定要不要转身体）和客户端（画头/瞳孔）用**同一组数**。
两边各写一份就会漂移，漂移不报错只出错（v1.12.9 的教训）。

### 3.2 数据面：实体加 4 个同步字段

`AvatarEntity`：

```java
private static final EntityDataAccessor<Float> GAZE_YAW   = SynchedEntityData.defineId(...);
private static final EntityDataAccessor<Float> GAZE_PITCH = ...;
// 瞳孔像素偏移也可以由客户端从 residual 算；若想单点权威就再存 2 个
```

- 只在**值变化超过 0.5°** 时 `set`（避免每 tick 都发）。
- `readAdditionalSaveData/writeAdditionalSaveData` 不必存（纯表现态，重登归零即可）。

### 3.3 服务端：头先转，到限位才转身体

`tickViewLock` 改成：

```java
double targetYaw = aim.yaw(), targetPitch = aim.pitch();
double delta = FacingMath.deltaDeg(self.getYRot(), targetYaw);   // -180..180
double headYaw = AvatarGaze.clampHeadYaw(delta);
if (Math.abs(delta) > AvatarGaze.HEAD_YAW_LIMIT) {
    // 头已到限位：身体按 BODY_TURN_PER_TICK 追（**不是瞬间对齐**）
    setRotation(self, AvatarGaze.bodyStep(self.getYRot(), targetYaw), self.getXRot());
}
self.setGaze(headYaw, AvatarGaze.clampHeadPitch(targetPitch - self.getXRot()));
```

这样行为是：目标在 40° → 只转头；在 90° → 头转到 65°，身体每 tick 再转 6°，两者一起把人/物"对进来"。

### 3.4 客户端：读同步值，不用 `netHeadYaw`

`setupAnim` 里把 head 与瞳孔的输入换成实体的 `getGazeYaw()/getGazePitch()`，
并用 `Mth.rotLerp(0.35F, last, target)` 做客户端平滑（服务端 20Hz，不插值会一跳一跳）。

瞳孔用**残余角**：

```java
double residual = entity.getGazeYawTarget() - entity.getGazeYaw();  // 超出头的部分
pupilX = AvatarGaze.pupilX(residual);   // 已经在眼里，不会出眶
```

## 四、必须先定的一处：截图视角（否则整套是"自相矛盾"）

头领先身体后，`PovCapture` 抓到的画面 = **身体朝向**，与模型"我在看 X"差最多 65°。
两个选项：

| 方案 | 做法 | 代价 |
| --- | --- | --- |
| **A（推荐）相机跟随视线** | 抓帧时把相机 yaw/pitch 设成 `bodyYaw + gazeYaw` / `bodyPitch + gazePitch`（请求里带上，或客户端直接读实体同步值算） | 改动集中在 `PovCapture`；好处是"看哪里拍哪里"，与 `vision_scan` 的射线方向一致 |
| B 视线不转头 | 只有瞳孔动，头随身体 | 最简单，但"转头"这个需求就名存实亡 |

`vision_scan` 也用的是 `getViewVector()`（= 身体），方案 A 之后两者天然一致；方案 B 则会出现
"扫描说前方是空地、照片里却是墙"。

## 五、约束与优先级

1. **优先级**：视角锁定 > 移动朝向（`faceMovement`）> 静止归零。
   现有 `faceMovement` 已经写了 `if (lookLock.locked()) return;`，与这条一致——**不要动它**。
2. **六条解除路径**（解锁/目标消失/玩家动鼠标/超时/超距/死亡）都必须把 gaze 归零；
   否则解除锁定后头会歪着不动（"卡住脸"）。
3. **瞳孔物理极限**：眼白 2px、瞳孔 1px，理论 ±0.5px；现用 ±0.2px 是为留边。
   超过 ±0.35 就会在侧视角露缝（此前"瞳孔外移即悬空"的教训）。
4. **不要动 `yHeadRot`**：走自定义同步字段，避免与 `PathfinderMob` 的 `LookControl` 抢写
   （Mob 每 tick 会按自己的 look control 改 `yHeadRot`，我们改它等于和引擎打架）。

## 六、风险表

| # | 风险 | 表现 | 怎么发现 |
| --- | --- | --- | --- |
| R1 | `setupAnim` 直接给 `head.yRot` 赋值 | 若 head 组有初始角会被抹平（本模型 head 初始角为 0，暂时没暴露） | 改成 `resetPose()` 后 `+=`，与瞳孔同一写法 |
| R2 | 客户端 20Hz 抖动 | 头一格一格地跳 | `rotLerp` 插值；断言"连续两帧差值 < 阈值" |
| R3 | 瞳孔越界露缝 | 侧面看眼睛有黑边 | 夹 ±0.2px；截图侧视验证 |
| R4 | 解除锁定后 gaze 不复位 | 头歪着不动 | 六条路径逐一断言 gaze=0 |
| R5 | 截图与视线不一致 | 模型说"看到墙"、照片是空地 | §四 方案 A；真机：把目标放 90° 侧后方，2 秒后截图应正对目标 |
| R6 | 与移动朝向抢 | 边走边看时头/身体抖 | 优先级铁律 + 断言"移动中锁定不解除" |

## 七、实施步骤

| 阶段 | 内容 | 验收（不依赖客户端的部分先做） |
| --- | --- | --- |
| P0（0.5d） | `AvatarGaze` 纯函数 + 单测（夹取/步进/瞳孔映射） | `gradlew :entitytools:test` 新增 8–10 条 |
| P1（0.5d） | 实体 4 个同步字段 + 访问器 + 变化阈值 | 单测：set 后读回、无变化不重复 set |
| P2（0.5d） | `tickViewLock` 改成"头先转 + 超限转身体" | 真机：目标 40° 只转头；90° 头到 65° 后身体开始追 |
| P3（0.5d） | `setupAnim` 读同步值 + 插值 + 瞳孔残余 | 截图看头/瞳孔是否跟着动 |
| P4（0.3d） | 截图视角跟随视线（方案 A） | 目标放侧后方，2 秒后截图应正对它 |

工作量 **1.5–2 天**；风险集中在 P2/P4，P0/P1 可以完全离线验。

## 八、待裁决

1. **限位数值**：头 ±65°、俯仰 ±35°、身体 6°/tick（120°/s）——够不够"像活的"？
   参考：猫头可转约 ±90°，但 MC 模型脖子只有一段，±65° 已接近"橡皮脖"。
2. **截图视角走 A 还是 B**（我强烈建议 A，否则"转头"与"看图"会互相矛盾）。
3. **是否要"瞳孔先动、头后动"**：即小角度（<15°）只动瞳孔、头不动，超过再动头。
   更像真猫，但多一层判据（`AvatarGaze` 加一个 `EYE_ONLY_LIMIT`）。
