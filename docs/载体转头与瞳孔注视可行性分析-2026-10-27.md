# 载体转头与瞳孔注视 · 可行性分析（2026-10-27 18:15 (UTC+8) 修订 v2）

> 命题（用户原话）："给载体加上转头和瞳孔移动，绑定指向到查看类工具查看的位置，或者锁定的生物，
> 限制转头和瞳孔移动幅度，抵达上限但仍未到就轻微移动身体朝向。"
>
> 追加（用户 18:12 (UTC+8)）："在控制朝向时默认也先转头，移动时收束至同一方向（除非有锁定的生物，
> 看向最近的锁定生物）。同时头部转向需要平滑一点防止多点切换导致观感抽搐。"
>
> 对象：snowleopard-framework 1.13.3（内嵌 core 0.6.1）· 载体 `snowleopard:avatar`

---

## 一、结论

**可行，2.5–3 天。** 与原版（1.5–2 天）相比多出的部分不是"转头"本身，而是**把朝向从"一次性赋值"
改成"持续目标 + 三级渐进 + 限速平滑"**——这是追加需求（控制朝向/移动收束/防抽搐）带来的结构性变化，
比重做模型动画小得多，但比"加两个同步字段"大。

| 要做的 | 现状 | 难度 |
| --- | --- | --- |
| ① 头部朝向跟随注视目标 | 模型**已经**支持 `head.yRot/xRot`，但输入恒为 0（§三.1） | 低 |
| ② 瞳孔随残余角平移 | 模型已有 `±0.2px` 平移，同样输入恒为 0 | 低 |
| ③ 三级渐进（瞳孔 → 头 → 身体） | 现在是**整体瞬间转身体**，没有"头"这一级 | 中 |
| ④ 截图视角与视线一致 | 相机取的是**身体** yaw/pitch | 中（口径，§五） |
| ⑤ **朝向统一由"持续目标"驱动** | `look()` 是一次性 `setRotation`，没有"追"的过程 | 中 |
| ⑥ **平滑与防抽搐** | 客户端无插值；服务端无目标调度无迟滞 | 中（新增，最易做出"抽搐"） |

一句话：③④⑤⑥ 各自都不难，**但它们必须共用同一个"视线状态"**，否则会互相抢写
（移动要转身体、凝视也要转身体、`look` 又要直接赋值），表现就是头在几个方向间跳——正是要防的"抽搐"。

## 二、裁决记录（v2 已定，不再讨论）

| # | 裁决 | 落地位置 |
| --- | --- | --- |
| 1 | 限位数值**可行**：头 ±65° / 俯仰 ±35° / 身体 6°/tick | `AvatarGaze` 常量 |
| 2 | 截图视角走 **A：相机跟随视线** | `PovCapture` + `vision_scan` 射线口径 |
| 3 | **要**"瞳孔先动、头后动" | 三级渐进（§四.2），靠**各自限速**自然涌现，不写静态分配 |
| 4 | **瞳孔是平移运动**（不是旋转） | 只改 `ModelPart.x/.y`；**禁止** `xRot/yRot`（§四.7） |
| 5 | **控制朝向也默认先转头** | `look` 改为设持续目标，不再是 `setRotation`（§四.3） |
| 6 | **移动时视线收束到移动方向**，除非有锁定生物则看向它 | 目标来源调度（§四.3）+ 身体权威（§四.4） |
| 7 | **头部转向平滑，防多点切换抽搐** | 三层平滑（优先级+驻留 / 限速+最短弧 / 客户端插值）（§四.5） |

裁决 6 有一处**推翻了上一版**：`faceMovement` 里现有的 `if (lookLock.locked()) return;`
（锁定期间不转身体）要改。原因见 §四.4——锁定期间若身体不转，`goto` 会变成"侧着滑过去"，
与"移动收束至同一方向"直接冲突。

## 三、现状盘点（都有代码位置）

### 3.1 模型侧：能力齐了，输入是死的

`client/model/SnowLeopardModel.java#setupAnim`（:328-345）：

```java
// 瞳孔：随头部朝向做微小偏移（±0.2px）。
float gazeX = Mth.clamp(netHeadYaw * 0.008F, -0.2F, 0.2F);
float gazeY = Mth.clamp(headPitch * 0.006F, -0.15F, 0.15F);
this.eyePupilLeft.resetPose();
this.eyePupilLeft.x += gazeX;      // ← 平移（PartPose 位移），不是旋转
this.eyePupilLeft.y += gazeY;
```

`netHeadYaw` / `headPitch` 由 `LivingEntityRenderer` 传入 = `yHeadRot - yBodyRot`。

**这条印证裁决 4**：瞳孔原来就是平移，且写入的是 `x/y`（模型局部平面内），
`resetPose()` 之后再 `+=` 是因为 `ModelPart.x/y/z` 本身就是 `PartPose.offset` 的基准
（v1.12.2 直接赋值把基准抹掉，瞳孔掉到下颚正中）。继续沿用这个写法即可，
**不要**改成 `xRot/yRot`：瞳孔是 1×1×1 的方块，绕自身中心转 10° 在视觉上几乎看不出来，
只有平移才能表达"看向某一侧"。

### 3.2 锁定侧：整体转身体，所以头永远是正的

`mc/EntityToolsModule.java#tickViewLock`（:566-582）：算出 `aim` 后直接

```java
setRotation(self, aim.yaw(), aim.pitch());   // body yaw = 目标方向
```

→ `yHeadRot ≈ yBodyRot` → `netHeadYaw ≈ 0` → **头不转、瞳孔居中**。
"看起来像机器人"不是模型不会动，是**上游把差值喂成了 0**。

### 3.3 显式 look 是一次性赋值（支撑裁决 5）

`mc/EntityToolsModule.java#look`（:358-374）：

```java
setRotation(self, yaw, pitch);   // 一帧到位，没有"追"的过程
lastSetYaw = yaw; lastSetPitch = pitch;
```

所以"控制朝向时也先转头"**不能靠加一个 if 实现**：`look` 必须改成"设一个持续目标"，
再由每 tick 的渐进逻辑把瞳孔/头/身体依次带过去。否则"先转头"只是同一帧内转完，看不出先后。

### 3.4 同步面：一个自定义字段都没有

`AvatarEntity extends PathfinderMob`，只有 `boundModel` 一个普通字段，
**没有 `defineSynchedData` / `SynchedEntityData`**。
服务端算出的注视角度目前**没有任何通道**能到客户端——必须补。

### 3.5 截图：相机跟的是身体

`client/vision/PovCapture.java`（:66）用 `mc.setCameraEntity(e)` 抓帧，相机取 `e.yRot / e.xRot`。
头领先身体后，照片会**落后于视线**。

## 四、设计

### 4.1 常量（`AvatarGaze`，纯 Java 可单测）

```java
double HEAD_YAW_LIMIT   = 65;    // 头相对身体的最大偏航
double HEAD_PITCH_LIMIT = 35;    // 头最大俯仰
double EYE_ONLY_LIMIT   = 15;    // 瞳孔能独立覆盖的角度（超过才动头）
double BODY_YAW_STEP    = 6;     // 身体追视线的速度（°/tick，120°/s）
double GAZE_SLEW        = 12;    // 视线（含瞳孔）追目标的最大角速度（°/tick）
double HEAD_SLEW        = 8;     // 头追视线的最大角速度（°/tick）——比 GAZE 慢 = "瞳孔先动"
double PUPIL_MAX_PX     = 0.2;   // 瞳孔平移上限（眼白 2px，物理极限 ±0.5）
double PUPIL_MAX_PY     = 0.15;  // 垂直上限（眼睛比宽扁）
int    SWITCH_DWELL     = 10;    // 换目标后的最小驻留（tick，200ms）
```

**为什么放共享类**：服务端（决定转不转身体）与客户端（画头/瞳孔）必须用**同一组数**；
两边各写一份必漂移，漂移不报错只出错（v1.12.9 的教训）。

### 4.2 三级渐进（核心：不写"先瞳孔后头"，让速率自己涌现）

每 tick 维护两个**世界角**：`gazeYaw`（视线已到哪里）与 `headWorldYaw`（头已到哪里）。

```java
// ① 视线追目标（快）
gazeYaw     += clamp(wrap(targetYaw - gazeYaw),        ±GAZE_SLEW);
headWorldYaw+= clamp(wrap(gazeYaw    - headWorldYaw),  ±HEAD_SLEW);   // ② 头追视线（慢）

// ③ 派生给渲染与身体
headRel    = wrap(headWorldYaw - bodyYaw);                 // 头相对身体
pupilAngle = wrap(gazeYaw - headWorldYaw);                 // 视线领先头的部分 → 瞳孔吃
pupilX     = pupilAngle / EYE_ONLY_LIMIT * PUPIL_MAX_PX;   // 线性映射，夹 ±0.2
```

观感过程（目标突然出现在右侧 40°）：

| tick | 视线 gazeYaw | 头 headWorldYaw | 瞳孔 | 观感 |
| --- | --- | --- | --- | --- |
| 0 | 0 | 0 | 0 | 静止 |
| 1 | 12 | 8 | 偏 4° → 0.05px | 眼珠先动 |
| 2 | 24 | 16 | 偏 8° → 0.11px | 眼珠继续 |
| 3 | 36 | 24 | 偏 12° → 0.16px | 接近上限 |
| 4 | 40 | 32 | 偏 8° | 头追上，瞳孔回中 |
| 5 | 40 | 40 | 0 | 头到位，眼珠回正 |

**这就是"瞳孔先动、头后动"**——不需要额外规则，只需要 `GAZE_SLEW > HEAD_SLEW`。
反过来若把两个速率写成同一个值，瞳孔会一直居中，等于没做。

超过 65° 时（比如 120°）：头卡在 ±65，剩下的 `gazeYaw - headWorldYaw` 还会增长，
但瞳孔夹在 ±0.2px，此时由**身体**每 tick 6° 追（§4.4 的非移动情形），
即"抵达上限但仍未到就轻微移动身体朝向"。

### 4.3 目标来源调度（裁决 5、6 的落点）

每 tick **只选一个**目标，按优先级：

```java
if (lookLock.locked())                 target = 锁定目标方向;      // 最高：生物/方块
else if (moveM.running())              target = 行进方向;           // 移动收束
else if (explicitLook != null)         target = explicitLook;       // look 设定的持续目标
else                                   target = 身体当前朝向;       // 归零
```

- **`look` 改为设 `explicitLook`**（不再 `setRotation`）：模型调 `look(yaw=90)` 而身体朝 0 时，
  眼镜先转 15°、头转到 65°、身体按 6°/tick 跟上，最终身体 90°、头回中。
  响应里要如实说"这是目标，头/身体会逐步转过去（约 X tick）"，否则模型以为一帧就到位。
- **移动收束**：`moveM.running()` 时目标 = 行进方向。没有锁定时视线与身体同向，
  不再"边走边看旁边"；有锁定时视线给锁定目标（§4.4 处理身体）。
- **"最近的锁定生物"**：当前 `LookLockMachine` 只有**单个** `target`（`lockFace` 字符串 + `target` 字符串），
  所以"最近"在现结构下退化为"唯一那个"。若要真正支持多候选（锁定多只/监视列表），
  需要新增候选集合，且"最近"建议按**视线夹角**而不是空间距离判（决定转头幅度的是夹角，
  空间距离近但在身后的目标不该抢）。

### 4.4 身体权威：移动 > 凝视（解开抢写，这是"抽搐"的第二个来源）

- **移动中**：身体朝行进方向，**凝视不转身体**。视线在侧面 >65° 时，头到限位就停住，
  视觉上是"边走边侧头看"，很自然。
- **非移动**：身体由凝视超限驱动——`|headRel| > HEAD_YAW_LIMIT` 时 `bodyYaw += ±BODY_STEP`。

因此 `faceMovement`（`EntityToolsModule#actuate`）**去掉** `if (lookLock.locked()) return;`：
移动时永远让身体朝行进方向，锁定只影响视线。这推翻上一版"锁定期间跳过"的写法
（当时的理由是不跟 `look_at` 抢；现在两者不再抢，因为身体权威已经按"是否移动"分开了）。
**速度、路径、DONE/BLOCKED 判定一律不动**——只动朝向。

### 4.5 平滑三层（裁决 7：防多点切换抽搐）

抽搐有三种成因，对应三层，缺一层都会看到：

| 层 | 手段 | 治什么 |
| --- | --- | --- |
| 目标选择 | **优先级抢占 + 最小驻留 10 tick**（同级/降级要等驻留满） | 两个目标夹角相近时每 tick 互相顶替 → 头左右摆 |
| 角度推进 | **限速**（`GAZE_SLEW` / `HEAD_SLEW` / `BODY_YAW_STEP`）+ **最短弧归一化** `wrap()` | 目标突变时瞬移；±180° 处绕远路（看起来像"抽一下再转回来"） |
| 渲染 | 客户端 `Mth.rotLerp(0.4F, last, target)` | 服务端 20Hz、客户端更高帧率 → 一格一格跳 |

最短弧尤其关键：`wrap()` 必须把差值归一到 `[-180, 180]`。否则从 `yaw=179` 到 `yaw=-179`
会走 358° 的长路，视觉上就是"猛地抽一整圈"。

**实现说明（落地后按代码改正）**："迟滞 15°"没有做成独立常量——当前锁定只有**单个**目标，
没有"多候选互相顶替"的情形，加一个用不上的阈值等于死代码。实际生效的是
**来源优先级（LOCK > MOVE > LOOK > IDLE）可立即抢占，同级或降级要等 10 tick 驻留期满**；
将来真要支持多锁定目标，再在"选哪一个"这步加夹角迟滞（判据用视线夹角，不用空间距离）。

### 4.6 数据面：实体加 4 个同步浮点

`AvatarEntity`：

```java
private static final EntityDataAccessor<Float> HEAD_YAW_REL   = SynchedEntityData.defineId(...);
private static final EntityDataAccessor<Float> HEAD_PITCH_REL = ...;
private static final EntityDataAccessor<Float> PUPIL_X        = ...;
private static final EntityDataAccessor<Float> PUPIL_Y        = ...;
```

- **直接同步最终值**（头相对角 + 瞳孔像素），不同步世界角：客户端不需要知道视线世界角，
  也不需要复算映射，避免两边算法漂移。
- 只在变化超过阈值（0.5° / 0.02px）时 `set`，避免每 tick 发四个包。
- 不写 `writeAdditionalSaveData`（纯表现态，重登归零）。

### 4.7 客户端渲染（沿用平移写法）

```java
float hy = Mth.rotLerp(0.4F, lastHeadYaw,   entity.getHeadYawRel());
float hp = Mth.rotLerp(0.4F, lastHeadPitch, entity.getHeadPitchRel());
this.head.resetPose();
this.head.yRot += hy * (π/180);        // ← 必须 +=，不能 =（R1）
this.head.xRot += hp * (π/180);

this.eyePupilLeft.resetPose();
this.eyePupilLeft.x += entity.getPupilX();   // ← 平移，裁决 4
this.eyePupilLeft.y += entity.getPupilY();
// 右眼同值：两个瞳孔同向平移（MC 玩家模型的规矩，别镜像）
```

## 五、截图视角：走 A（已裁决）

头领先身体后，`PovCapture` 抓到的画面 = **身体朝向**，与"我在看 X"差最多 65°。

**A 方案**：抓帧时把相机设成 `bodyYaw + headYawRel` / `bodyPitch + headPitchRel`
（客户端直接读实体同步值算，不需要额外传参）。

顺带统一 `vision_scan`：它用 `getViewVector()`（= 身体朝向），也要改成合成朝向。
否则会出现"扫描说正前方是空地、照片里却是墙"——两个工具对"前方"的定义不一致，
模型会认为是自己搞错了，进而怀疑工具。

## 六、约束

1. **不改 `yHeadRot`**：`PathfinderMob` 的 `LookControl` 每 tick 会写它，我们改等于跟引擎打架。
   走自定义同步字段 + 客户端渲染层偏移。
2. **六条解锁路径**（解锁/目标消失/玩家动鼠标/超时/超距/死亡）都必须把 gaze **平滑归零**，
   否则解除后头歪着不动（"卡住脸"）。归零不是瞬间置 0，走同一套限速。
3. **瞳孔边界**：眼白 2px、瞳孔 1px，理论 ±0.5px；用 ±0.2/±0.15 留边。
   超过 ±0.35 在侧视角会露缝（"瞳孔外移即悬空"的旧教训）。
4. **优先级总表**（写进代码注释与 check）：
   `锁定 > 移动收束 > 显式 look > 归零`；**身体权威** `移动 > 凝视`。

## 七、风险表

| # | 风险 | 表现 | 怎么发现 |
| --- | --- | --- | --- |
| R1 | `setupAnim` 直接给 head 赋值 | 头组初始角被抹平 | 一律 `resetPose()` 后 `+=`，与瞳孔同写法 |
| R2 | 客户端不插值 | 头一格一格跳 | `rotLerp`；断言"连续两帧差值 < 阈值" |
| R3 | 瞳孔越界露缝 | 侧看有黑边 | 夹 ±0.2/±0.15；侧视截图验证 |
| R4 | 解锁后 gaze 不复位 | 头歪着不动 | 六条路径逐一断言归零 |
| R5 | 截图与视线不一致 | 说"看到墙"、照片是空地 | 方案 A；目标放 90° 侧后方，2 秒后截图应正对 |
| R6 | **多点切换抽搐** | 头在两个方向间来回摆 | 优先级抢占 + 驻留 10 tick + 限速；构造"两只等距生物"场景验证 |
| R7 | **±180° 绕远路** | 头猛抽一整圈 | `wrap()` 归一化；断言 179→-179 只走 2° |
| R8 | **移动与凝视抢身体** | 边走边抖 | 身体权威 = 移动优先；断言"移动中锁定不转身体" |
| R9 | `look` 语义变化 | 模型以为一帧到位，紧接着截图拍到旧方向 | 响应里写"逐步转，约 X tick 到位"；截图前用 `view_status` 确认 |
| R10 | 同步字段每 tick 发 | 带宽浪费、远处实体更新抖动 | 变化阈值 0.5°/0.02px |

## 九、落地结果（2026-10-27 18:42 (UTC+8)，v1.14.0）

**真机 36 PASS / 0 FAIL**（基线 34 + 新增 2 条视线断言），单测 96 项全绿（新增 14 条 AvatarGaze）。

实测数值与设计一致：

| 断言 | 实测 | 含义 |
| --- | --- | --- |
| 第一 tick | `pupil1=0.0533`、`head1=8.0` | 瞳孔已偏 4°（4/15×0.2px），头才 8° → **眼先动** |
| 小角度 40° 收敛 | `headEnd=40.0`、`pupilEnd=0.0`、`bodyYaw` 不变 | 只转头、瞳孔回中、**身体不动** |
| 大角度 120° 收敛 | `bodyTurned=60.0`、`headRel=60.0`、`composed=30.0`（= target） | 身体转到"差 65°"附近停，**合成视线正对目标** |

### 落地踩到的两个坑（都已修，写下来防重踩）

1. **复位只 reset 内部状态、没清同步字段**：`unlock` 后实体上仍挂着 `headRel=60`，客户端照读，
   于是扫描射线比身体偏 60° → "视觉射线沿视线命中"回归失败，看着像产品坏了。
   修法：`resetGaze()` 同时 `applyGaze(0,0,0,0)`；观感仍平滑，因为客户端有 `rotLerp` 插值。
2. **新增断言改了旧断言的场景前提**：k6 把载体真转到 120°，而后续视觉断言的红羊毛是
   "按当时朝向临时摆放"的 → 朝向一变就摆到别处，表现为假回归。
   修法：断言结束**恢复体位**（`setYRot/base`、`setXRot(0)`）再解锁。
