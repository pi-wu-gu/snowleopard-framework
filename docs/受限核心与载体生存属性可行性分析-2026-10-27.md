## 一、结论

**可行，约 9 天（9.25 天）。** 与 v1 相比有两处结构性变化，都是裁决①带来的：

1. **核心不再是"方块=家"**，而是**家目录的创建/绑定凭证**（一套"钥匙"）。所以 v1 里"放出方块 +
   spawn 实体"的流程作废，改成"界面里建家/绑家"。
2. 由此多出一条此前没有的能力链：**核心绑定家 → 右键对应载体 → 经验传输 / 付费传送**。
   它同时是安全边界（必须找到实体才能操作，不能纯界面远程遥控所有家）。
3. **v3 澄清**：原「核心传输」指**经验传输**（玩家把经验给载体）；另新增**传送**——
   **消耗经验把指定载体叫到玩家身边，按距离收费**。两项都走「右键对应载体」，都不接受界面远程选中。

## 二、模型解析与形态（裁决①之后）

`受限核心.bbmodel`：`format_version 5.0`、`model_format = java_block`、`resolution 16×16`、10 个 cube
（中心 2×2×2 + 内嵌 1×1×1 + 八角 0.95~1.05 卡扣），整体 `6.95→9.05` ≈ **2.1 格**。

裁决①之后，模型**不再是"要放下的方块"**，而是核心物品的外观。落地形态建议保留、但降级为可选：

| 形态 | 做法 | 说明 |
| --- | --- | --- |
| **物品（主）** | BlockItem（对方块模型），inventory 里就是那个立体装置 | `java_block` 模型可直接作 block item 的模型 |
| 摆放（次） | **潜行右键**才放置纯装饰方块（无方块实体、无逻辑） | 保留"能摆出来看"的可能；右键不放置，避免与"弹界面"抢 |

> **右键语义**：普通右键 = 弹界面（裁决①）；**潜行右键 = 放置**。这与原版"右键放置、潜行使用"相反，
> 必须在 tooltip 与文档里写明，否则玩家第一反应是"右键没放下"。
>
> **与 §3.6 的"潜行右键载体 = 传送"不冲突**：两者目标不同、事件也不同——落在**方块/空气**上走
> useOn（放置装饰方块），落在**载体实体**上走 EntityInteract（付费传送）。手持物也不同（核心 vs 核心），
> 所以不会互相抢；但实现时必须按"目标类型"分流，不能只在 `use` 里判潜行。

2.1 格视觉 > 1 格碰撞箱：装饰方块建议 `noOcclusion` + 碰撞箱按 1 格收窄（或直接无碰撞），
避免站在旁边被无形挡道。

## 三、九条裁决的落地设计

### 3.1 核心 = 家目录的钥匙（裁决①）

现有家目录：core 的 `Ids.home(caller)` → `ids/<ID>/`（挂载隔离 + 路径锚定，越界即拒）。
所以"创建家"= 让 core 在 `ids/` 下建一个 ID 目录并完成登记，"绑定家"= 让手中这枚核心指向某个已存在的 ID。

**枚举一下"家"是什么**（避免后面口径漂移）：一个 ID ＝ 一个模型编号（如 `clienttest`），
它拥有自己的 `ids/<ID>/`（记忆/笔记/待办/工具配置/审计）与 `avatars.json` 里的载体登记。

| 分支 | 触发 | 消耗核心 | 服务端动作 |
| --- | --- | --- | --- |
| **创建家** | 界面输入新 ID | **不消耗** | 建 `ids/<ID>/`（含最小骨架）→ 登记为"空家"；**核心仍是未绑定**（不写 NBT）——否则「绑定要消耗」形同虚设 |
| **绑定家** | 界面选已有 ID | **消耗 1** | 校验 → `shrink(1)` → 新核心物品 NBT `home=<ID>`（这枚核从此是那家的钥匙） |

**"创建家不消耗"的含义**（我按这个实现，若有偏差请纠正）：创建是**从零开一个空家**，不占用已有资源，
所以免费；而绑定是**获得某家已有资产的钥匙**（能看经验、改配置、传输载体），所以收费。

由此推出一条必要约束：**创建家 ≠ 自动绑定**。否则"不消耗"就等于白拿钥匙。

### 3.2 界面与两条分支的原子性（裁决①、⑧）

**界面是表单，不是授权**——这是整条链路唯一会造成数据事故的地方（重发包 / 断线重连 / 双开刷物品）：

1. 右键核心（未绑定）→ 客户端开 `CoreScreen`，列出已有家 + "创建新家"输入框。
2. 选择后发 `CoreAction(action=CREATE|BIND, homeId, expectedStackNonce)`。
3. 服务端**四道校验**：① 手持确是核心；② `expectedStackNonce` 与当前手持物品一致（防界面过期）；
   ③ `homeId` 合法（新家：不存在 + ID 规则；绑定：存在）；④ 该家是否已有绑定核心（**一核心一家**，见 R2）。
4. 通过才执行（创建：建目录；绑定：`shrink(1)` + 写 NBT），**同一 tick 内完成，失败不留半成品**。

已绑定的核心右键 → 直接开该家的配置界面（不再弹选择）。

### 3.3 经验：可配置（实体属性）+ 模型可读 + 核心可看（裁决②④）

| 项 | 设计 | 落点 |
| --- | --- | --- |
| 存储 | `xp`（int）+ 配置项 `xpPerHp`（兑换比）、`hpPerTick`（回血速率）、`xpPerSecCap` | **实体字段 + NBT**（裁决④明确"属性在实体而非家"） |
| 默认值 | `xpMax = 1000`、`xpPerHp = 2`（2 经验=1 血）、`hpPerTick = 0.5`、`xpPerSecCap = 20` | 可在核心界面改（写回实体 NBT） |
| 来源 | 击杀（按血量折算）、经验瓶、核心界面测试充值（裁决③"全"） | 击杀挂 LivingDeathEvent（现在只用来解绑，需扩展） |
| 模型可读 | 新工具 `avatar_vitals`（只读：xp/hunger/血/上限）+ **每轮注入一行**（见下） | `ToolSchemas` + 注入 |
| 玩家可看 | 核心界面顶部显示（裁决⑧"均需要"） | `CoreScreen` |

**"确保模型能获取经验量"我建议做成双保险**：
- 工具 `avatar_vitals`（模型主动查，和现有 `self_status` 同类，不新增组）；
- **注入**：TURN_END 那一处加一行（`血 12/20 · 经验 60/1000 · 饥饿 5/20`）。
  理由：模型不会主动查状态（这是 `tool_help` 0 次调用证明过的行为模式），只有注入才是"它真的知道"。

### 3.4 饥饿 + 进食 + 主副手投喂（裁决⑤⑥）

| 项 | 设计 |
| --- | --- |
| 存储 | `hunger`（0–20），随时间递减（缺省 30 秒 -1，可配） |
| 影响 | `hunger == 0` → **不能**用经验回血 + 移速 ×0.85（裁决⑤"连带"）；`hunger ≥ 6` 才能自然回血 |
| 自行进食 | 工具 `avatar_eat(slot?)`：从背包取食物（DataComponents.FOOD，1.21 无 `isEdible`），按 `nutrition` 回饥饿 |
| 右键投喂 | 手持食物右键载体 → 消耗 1 → 回饥饿 + 少量血 + 回执 |

**主副手优先级（裁决⑥）**：

```
主手是可用物品（食物 / 核心）→ 用主手
主手不可用、副手可用         → 用副手
两侧都可用                  → 主手
空手                        → 唤醒（现有行为）
```

> 注意 1.21 的 PlayerInteractEvent.EntityInteract **会为主手和副手各触发一次**。必须显式过滤：
> 只在 `event.getHand() == InteractionHand.MAIN_HAND` 时处理"两手都可用"的情形，否则一次右键会喂两口。

### 3.5 唤醒限制改造（裁决⑨，跨仓）

现状：配额在 core —— `WakeStore.QUOTA_PER_WINDOW = 48`，按**目标 ID**（`toId`）在 1 小时窗口内计数。
而冷却（LAST_WAKE）已经按**载体 uuid**。裁决⑨要求"计数与余量绑定实体"，所以要动两层：

| 层 | 改动 |
| --- | --- |
| core（0.6.2） | WakeStore 支持**配额可配**（`0 = 不限`）；`policy()` 回执带上当前配额与已用数，便于界面显示 |
| shell | 限流主逻辑移到 `AvatarWake`，**按 `avatar.getUUID()`** 记"本小时已唤起 N 次 / 余量 M"；计数与余量存**实体 NBT**（跨重启保留，符合"绑定实体"） |
| 默认 | **暂时移除限制**（配额 = 0），但界面可开启并设上限（裁决⑨） |

> 顺带修一个旧坑：配额满时玩家只看到"唤醒被拒绝"，不知道原因。界面里显示余量后，这类"看起来坏了"
> 就变成"看得见的规则"。

### 3.6 右键载体：经验传输 + 付费传送（裁决③，v3 澄清）

原句「核心传输」指**经验传输**；确认后还要**传送**这一项。两者共用一条前置：
**手持已绑定核心 + 右键某个载体实体**（不接受界面远程选中——这是安全边界）。

| 能力 | 触发 | 费用 | 校验 |
| --- | --- | --- | --- |
| **经验传输** | 手持核心右键载体 | 扣**玩家**的 XP 点（`totalExperience`），加到载体 `xp` 池 | 核心 `home` == 载体的 `modelId`；玩家点数够；不超过载体 `xpMax` |
| **付费传送** | 手持核心**潜行**右键载体 | 扣**载体**经验，`cost = ceil(直线距离 × 每格费率)` | 同上；经验够付；落点安全；不打断进行中的动作 |

**为什么要分两个手势**：同一个右键不能既「给经验」又「传送」——那是最容易误触的组合
（想喂经验，却把正在挖矿的载体拉走）。用**潜行 + 右键**区分传送，回执里写明扣了多少。

**传送的三个真坑**（比「按距离收费」本身更容易出事）：

1. **打断进行中的动作**：载体可能正在 `goto` / 挖掘 / 锁定目标。瞬移后目标距离突变，`MoveMachine`
   会判成超距失败甚至继续朝旧目标走。做法：传送前**先停动作**（移动停止 + 挖掘中断），
   回执里说明「已中断它正在做的事」。
2. **落点不安全**：复用 `/snowleopard avatar spawn` 的落点查找（脚下实心 + 两格空气 + 格内无生物），
   找不到即拒绝并**不扣费**。
3. **跨维度**：默认**只在同维度生效**（跨维度还要处理 `changeDimension`，风险高于收益），
   拒绝时说明原因，不扣费。

**费用口径**（可配，住实体属性，与裁决④一致）：

- `tpCostPerBlock`（每格经验，缺省 0.5）→ 10 格 = 5 经验、100 格 = 50 经验；
- `tpCostMax`（单次封顶，缺省 200）→ 防止远距离把经验池一次掏空；
- 距离用**直线距离**（不绕路），回执同时给「距离 / 费用 / 剩余经验」，玩家能判断值不值。

> 裁决④要求「属性在实体而非家」，所以这三个费率住在**被传送的那个载体**身上，而不是 `avatars.json`。

### 3.7 界面范围（裁决⑧"均需要"）

一个 `CoreScreen`，两块内容：

- **顶部**：该家的载体列表（`AvatarStore.all()` 过滤 `modelId == home`），每行显示
  `血 12/20 · 经验 60/1000 · 饥饿 5/20 · 唤醒余量 N`（余量来自 §3.5 的实体计数）。
- **中部**：选中载体的配置——唤醒间隔（≥60s）、定时开关、经验兑换比、回血速率、饥饿递减间隔、
  唤醒限额（0=不限）、显示名。
- **底部**：`保存` / `创建家`（未绑定时）/ `绑定此家`（消耗提示写清"将消耗 1 个核心"）。

未绑定的核心只能看到"创建家 / 选择家"两栏；已绑定的才看到配置。
