# 聊天栏推送 · 可行性分析

> 2026-10-23 22:20 (UTC+8) · 对象：雪豹框架壳（MC 侧推送面）· 依据：用户要求「将聊天栏加入推送」
> 前置：轮末汇总已存在（核心 `TurnSummary`，一行：群未读 / 新消息 / 新唤起 / 记忆待吸收）
> 记录口径：`YYYY-MM-DD HH:MM (UTC+8)`

## 一、结论先行

**可行，且是"多一个出口"而不是"新造一套内容"**——同一条 `TurnSummary` 行同时有两个去处：

| 出口 | 谁看 | 形态 |
|---|---|---|
| 模型上下文尾注 | 模型 | 一行摘要（已有） |
| **玩家聊天栏** | 人 | **同一行** + `[雪豹]` 前缀（本次新增） |

**内容同源是关键**（不新建第二套文案）：否则"模型看到的"和"玩家看到的"迟早不一致，
而这正是最难发现的一类漂移（两边都"看起来对"）。

三条硬约束（不是可选优化）：

1. **只推摘要，不推正文**——群组消息是别的模型写的文本，整段推到聊天栏等于把不可信内容展示给人，
   且与"外来内容不自动全文注入"的原则自相矛盾；
2. **送达要有返回值**——无在线玩家时返回 `false` 并落日志，**绝不假装"已推送"**（假成功家族）；
3. **限流 + 去重**——同一行 5 秒内不重复、每分钟 ≤ 20 条；否则一个热闹的群能把聊天栏刷成瀑布。

## 二、渠道对比（为什么是聊天栏）

| 渠道 | API | 适用 | 缺点 |
|---|---|---|---|
| **聊天栏（system chat）** | `ServerPlayer#displayClientMessage(Component, false)` | **可回溯、可多行、不遮挡** | 会被玩家自己的输入刷走 |
| 动作栏（action bar） | 同上，`true` | 高频轻量（准心下方一闪） | 一闪而过，看不全 |
| 标题（title/subtitle） | `ClientboundSetTitleTextPacket` | 强提醒 | 打断操作，滥用招人烦 |
| BossBar | `ClientboundBossEventPacket` | 持续状态（血条式） | 一个 BossBar 只能显示一条，抢占严重 |

**选聊天栏**：告警是"事后可查"而不是"当场打断"；且与 MC 原生的系统消息（`[Server]`）同栏，玩家心智一致。
动作栏留作**将来**的高频补充（如"移动中"这类瞬时状态），本版不做。

## 三、发给谁（多人服务器的现实问题）

雪豹的"模型"没有 MC 玩家身份（它绑的是一个实体）。所以：

- **默认：发给所有真人玩家**（`PlayerList#getPlayers()` 逐个 `displayClientMessage`）——
  这是"服务器运营者能看见"的最朴素语义；
- **不做"只发给某玩家"**：模型与玩家之间没有归属关系，硬造一个（谁绑定的）会在多人场景变成新的权限面；
- **排除假人**：`FakePlayer` 也是 `ServerPlayer`（能收包但没有客户端）——推给它等于推给空气，
  所以默认实现跳过 `instanceof FakePlayer`（避免"看起来发了 3 个人，其实只有 2 个能看见"）。

## 四、无玩家环境（专用服务器/自测）怎么测

这是本功能的**可测性难点**：`runServer` 起的是专用服务器，没有任何客户端，聊天栏推送在真机上"看不见"。

**解法：`ChatPush.Sink` 注入点**（与 `Compressor`、`RuntimeView` 同一模式）：

```java
ChatPush.setSink(line -> RECORDED.add(line));   // 自测：记录而不发
ChatPush.push(line);                            // 内容/限流/去重逻辑照跑
```

- 生产：`sink == null` → 走真实玩家通道（无玩家 → 日志 + 返回 false）；
- 自测：注入 sink → 断言**内容与限流**，而不是"能不能看见"（后者在无客户端环境里永远无法断言）。

**这是"能不能测"的分界线**：没有注入点，这个功能只能靠人手看聊天栏，回归测试等于零。

## 五、限流与去重（防刷屏的具体数字）

| 规则 | 值 | 理由 |
|---|---|---|
| 同内容去重窗口 | 5 秒 | 轮末可能连发两轮，内容一样不该刷两次 |
| 每分钟上限 | 20 条 | 一个热闹群 + 多组提示的上界；超限**丢弃并 WARN**（不静默） |
| 单条长度 | ≤ 256 字符 | 聊天栏一行放不下更多；超长**截断并标注**（`…`），不静默丢 |

超限丢弃要记日志——"没推出去"这件事必须留痕，否则玩家会以为系统没在跑。

## 六、与既有机制的关系

| 机制 | 关系 |
|---|---|
| `TurnSummary`（核心） | **内容唯一来源**；壳只负责"送到哪" |
| `WakeBridge.consumeTurnLine` | 推送后调用：标"已提示"（模型上下文与聊天栏**共用同一次提示记账**，不会一个说"提示过"另一个说"没提示"） |
| 群组消息正文 | **永不推送**（只推计数）；玩家要看内容得自己进群/看日志 |
| 审计 | 推送失败/超限进日志（WARN），不改任何业务状态 |

## 七、风险表

| 风险 | 形态 | 对策 |
|---|---|---|
| **刷屏** | 高频轮末 + 多群未读 | 同内容 5s 去重 + 20/min 上限 + 超限 WARN |
| **假送达** | 无玩家却报"已推送" | `push` 返回 boolean；无玩家落日志并返回 false |
| **内容外泄** | 把群消息正文推给人 | 只推 `TurnSummary` 摘要行（计数），正文不出现在推送路径 |
| **双份文案漂移** | 模型一份、玩家一份 | 同一行两出口，**不新建文案** |
| **假人计数** | FakePlayer 也收包 | 默认实现跳过 `FakePlayer` |
| **截断歧义** | 超长被砍一半 | 截断处加 `…`，完整内容仍在日志 |

## 八、验收断言（M11，真机）

```
① 绑定中立生物：僵尸猪灵（ZombifiedPiglin，受击才反击）→ sense.open 见候选 → pick 成功
② 中立性旁证：未受击时它不把绑定方当目标（`getTarget()==null`）
③ 推送内容同源：ChatPush.push(TurnSummary.line(...)) → sink 收到的文本 == 该行
④ 前缀与长度：[雪豹] 前缀 + ≤256 字符
⑤ 去重：同一行 5 秒内推两次 → 只送达一次
⑥ 无玩家 + 无 sink：push 返回 false（不谎报送达）
⑦ 摘要不含正文：制造一条带正文的群消息，推送行里**不含**该正文
```

## 九、本版不做（明确记账）

- **动作栏（actionBar）高频通道**：留到有"瞬态状态"需求时再加；
- **按玩家过滤**（只推给管理者/OP）：需要新的权限面，本版不引入；
- **玩家侧界面**（点开看详情）：聊天栏是可点击的（`ClickEvent`），但那是"从推送跳到 UI"，属于下一层。
