# 蝙蝠捕获与物品拾取 · 可行性分析

> 2026-10-24 18:15 (UTC+8) · 需求方：用户（真机游玩后提出五条：抓蝙蝠存为物品（直接用蝙蝠模型）/
> 右键地面放走 / 右键空气吃掉按面包数值 / 给模型添加开关自动拾取 / 主动拾取指定物品的工具）
> 前置：框架 v1.9.5 真机 13 PASS（载体九格包、ItemIndex、视线 raycast 均已有）。
> **本次日志（17:52）实锤一个旧缺陷**（§四，drop/move 的 count），与本批工作同域，建议并入同一版顺手修。

---

## 一、结论总表

| 需求 | 判定 | 关键结论 |
|---|---|---|
| 抓蝙蝠 → 物品（直接用蝙蝠模型） | **可行** | 原版 `BatModel` + `textures/entity/bat.png` 可直接复用（1.21.1 实体渲染还是"直接摆模型"时代，无 render-state 中间层）；物品端走 BEWLR 自定义渲染；捕获动作=新增工具 `interact/capture`（载体视角，§3.1） |
| 右键地面放走 | **可行** | `Item.useOn` 返回 SUCCESS 即拦截，不会误触发进食 |
| 右键空气吃掉（面包数值） | **可行** | 注册物品时 `.food(new FoodProperties.Builder().nutrition(5).saturationMod(0.6f).build())`——原版进食流程全免费（举着右键、咀嚼动画、饱食度 5/饱和 6.0，与面包完全一致） |
| 开关自动拾取 | **可行（有一坑）** | 原版 `LivingEntity.aiStep` 自带拾取扫描（"looting"段），三个覆盖点接到载体九格包；**必须防"自己丢出去自己捡回"的反馈环**（§3.3，真机 17:52 场景刚好撞上） |
| 主动拾取指定物品 | **可行** | 新工具 `item/pickup`：半径扫描 ItemEntity + registry id 过滤 + 入包；远处先 `goto` 走过去再拾 |

**一句话总结**：五条全部可行、无硬阻塞。真正要小心的只有两处——**物品渲染的逐视角变换**
（§2.2，大概率要真机肉眼反复调）和**自动拾取的自丢反馈环**（§3.3）。
另外 §四 的 count 缺陷是这批需求"捡东西"场景的直接前置（模型现在连"按数量丢"都不对），
建议同一版本修掉，真机验收一次覆盖。

## 二、蝙蝠物品（含渲染）

### 2.1 注册面（四处，缺一就看不见或不工作）

| 面 | 做什么 | 备注 |
|---|---|---|
| `DeferredRegister<Item>`（注册表 `Registries.ITEM`，id 建议 `snowleopard:bat`） | `new Item(new Properties().stacksTo(?)​.food(面包数值))` | 挂 mod 事件总线（`AvatarEntities.register` 同款模式）；food 数值 = nutrition 5 / saturationMod 0.6（抄 `Items.BREAD`） |
| 物品模型 JSON（`assets/snowleopard/models/item/bat.json`） | BEWLR 只画几何，但 JSON 必须存在且带 display 定义 | 逐视角变换（背包格子/手持/掉落地/展示框）在 JSON 里定，几何由渲染器画 |
| `RegisterClientExtensionsEvent`（**仅客户端**） | `IClientItemExtensions.getCustomRenderer()` 返回自写 BEWLR | `AvatarClient` 已有 `@EventBusSubscriber(Dist.CLIENT)` 入口，加一条即可 |
| 服务端工具面 | `interact/capture`（§3.1） | 物品本身纯数据，服务端无逻辑 |

### 2.2 渲染：直接用蝙蝠模型（同"复用豹猫外观"先例）

- `BatModel(ctx.bakeLayer(ModelLayers.BAT))` + 原版贴图 `textures/entity/bat.png`——**零新资源**，
  与 `AvatarClient.AvatarRenderer` 复用豹猫是同一模式，先例已验证可行。
- `BatModel.setupAnim(Bat …)` 读的是 `Bat` 实体的休息/飞行标记 → 客户端 new 一个 **dummy `Bat`**
  （仅渲染用，绝不能出现在服务端类里）喂给 setupAnim，或直接手动摆 root 部件。两种姿态
  （平飞 / 倒挂）选一或都做，v1 建议只做**平飞**（倒挂是它最出名的姿态，但物品悬空倒挂反而难懂）。
- **最可能反复调的部分**：`BatModel` 原始尺寸按 0.9 方实体建模，直接画进 16px 的物品格子会爆格。
  需要在 BEWLR 内 scale（约 0.35–0.55）+ 旋转，且手持/背包/掉落三个视角要分别调 JSON display。
  与 `AvatarClient` 注释里那条"需真机肉眼确认"同理：**数字能算个起点，好不好看只能眼睛看**。
- 渲染器实例要**复用**（构造一次存字段），每帧 new 模型会闪退堆。

### 2.3 吃 / 放走语义（一次右键只发生一件事）

| 动作 | 钩子 | 实现 |
|---|---|---|
| 右键**地面**放走 | `useOn(UseOnContext)` | 取 `clickedOnPos.relative(context.getClickedFace())` 做出生点（简单空位检查防墙里），`level.addFreshEntity(new Bat(EntityType.BAT, level))`，物品 `shrink(1)`，返回 `SUCCESS` |
| 右键**空气**吃掉 | 不写——`Item.use` 默认实现检测 `FOOD` 组件自动走进食 | `.food()` 注册即得；饱食度满时原版自动不响应，"吃不掉浪费"免费获得 |

- `useOn` 返回 SUCCESS/CONSUME 后**不会**再进 `use`——一次右键"放走 XOR 吃掉"由原版分发顺序保证，
  不需要自己写互斥。
- **决策点**：玩家看着方块其实想吃怎么办。推荐 **潜行+右键反转语义**（蹲下右键方块=吃，
  站立右键方块=放走）；或 v1 从简：看着方块恒放走，想吃抬头。实现前须定（§六）。

### 2.4 两条边界，先说清

1. **和平模式放走=蒸发**：`Bat.checkDespawn` 在 PEACEFUL 直接 discard（与本仓"PEACEFUL 时
   checkDespawn 会 discard 生物"铁律同源）。这不是 bug，是原版行为——文档写明，测试房难度固定。
2. **"吃掉"只对玩家有意义**：载体没有饥饿值（`FoodData` 是玩家的），模型自己吃不了。
   模型对这件物品的操作=捕获（capture）、给玩家（drop/give）、放走（后续可加 use 类工具）。
   按面包数值补充的是**玩家的**饥饿。

## 三、拾取（自动开关 + 主动工具）

### 3.1 捕获工具 `interact/capture`

- 目标判定复用 attack 的视线 raycast（实体 AABB，限 ≤3.5 格、`instanceof Bat`）。
- 成功 = 目标 `discard()` + `pack.addItem(蝙蝠物品)`；**包满必须报错**（绝不静默丢地上——
  "假成功比失败更坏"家族）。
- v1 建议 100% 成功率、无冷却（蝙蝠非战斗资源，加随机只会让模型困惑）。
- **捕获主体=载体**（本方案）；"玩家空手抓蝙蝠"是另一套交互（玩家侧 mobInteract），v1 不做，
  留作后续选项。

### 3.2 自动拾取：走原版钩子（推荐），不走 goal

`LivingEntity.aiStep` 的 "looting" 段在 `canPickUpLoot()==true` 时自动扫描身边 ItemEntity →
`wantsToPickUp(stack)` → `pickUpItem(entity)`。`AvatarEntity` 只需三个覆盖：

| 覆盖点 | 内容 | 备注 |
|---|---|---|
| `canPickUpLoot()` | 返回自动拾取开关 | 原版 NBT 键 `CanPickUpLoot` **自动持久化**，开关白拿落盘 |
| `wantsToPickUp(ItemStack)` | 过滤：无 filter=全部；有 filter=registry id 匹配 | filter 存实体 NBT（自增 `PickupFilter`） |
| `pickUpItem(ItemEntity)` | **必须覆盖**：入九格包；原版默认实现按装备槽处理，会乱 | 含"自丢反馈环"判据（§3.3） |

- 这条路线**不违反"无原版 AI"契约**：拾取扫描是 `aiStep` 内联逻辑，不经 goal 系统，
  `registerGoals()` 仍然空。在 `AvatarEntity` 注释写明这一点，防止后人"清理"掉。
- 备选路线（自写 tick 扫描）完全可控但要自己处理 delay/去重/音效，代码反而更多。不推荐。

### 3.3 最大坑：自己丢出去自己捡回（反馈环）

**真机 17:52 场景直接撞上**：玩家要 8 木头+5 门 → 模型 `drop` → `spawnAtLocation` 生成掉落物 →
若此时自动拾取开着，0.5 秒（pickupDelay）后被自己捡回——**模型永远给不了玩家东西**，而且不报错。

修法一行判据：ItemEntity 的 `thrower` UUID 是原版持久化字段 →
**自动拾取跳过 `thrower==自己` 的掉落物**；主动 `pickup` 工具不受此限（模型明确点名要捡是例外）。
比"丢出后 N 秒冷却"稳：冷却依赖时间窗，thrower 判据依赖事实。

### 3.4 主动拾取工具 `item/pickup`（schema 草案）

```
pickup { item: "minecraft:slime_ball"（可选，registry id 或关键字过滤；缺省=附近全部）,
         radius: "4"（可选，扫描半径上限 6；触达判定 ≤2.5 格） }
→ Ok: { picked: [{item, count}…], skipped: [{item, reason: 包满|超半径|thrower==自己}] }
```

- 远处的东西不自动寻路：模型先 `goto` 走过去（history.jsonl:686 实证模型已经会这么推理——
  "Let me walk to those item positions"）。
- **模型认知差已实证**：同一条 reasoning 里模型先写"走过去就会自动捡"，又发现"slimeball 根本没被捡"。
  这批工具正好把这个落差补上。

## 四、日志新发现：drop / move_item 的 count 缺陷（真机 17:52 实锤）

**现象**：模型发 `{"count": "5", "from": "self:pack:3"}`（schema 里 count 是 string）→
`EntityToolsModule` 两处 `params.get("count") instanceof Number`（drop 1065 行、move_item 1028 行）
只认 Number → **静默整组**：木头丢 53 个、橡木门丢 18 扇。模型自己在 reasoning 里试了
"字符串→数字面量"两种写法都失败，最后只能如实向玩家坦白。

**定性**：v1.9.4 修 craft 时做过同款宽容解析（Number 或可 parse 字符串，1143–1148 行），
**但没同步到 drop / move_item**——"同一职责多实现必漂移"的又一实例，且是**假成功家族**
第二例（返回 `dropped=53` 当成功）。

**修法**：抽 `countParam(params, key, fallback, max)` 三处共用；自测补
`drop count:"n"` 只丢 n 个的断言（真机首轮 2 FAIL 的同款教训：**没断言的路径坏了没人知道**，
1.9.3 全绿就是假象）。

## 六、决策点（实现前须定）

1. **物品 id 与显示名**：`snowleopard:bat`/"蝙蝠"？还是叫"蝙蝠罐"暗示容器？
2. **可否叠放**：v1 蝙蝠无个体数据（1.21.1 无变种）→ 技术上可叠；但"每只独立 `stacksTo(1)`"
   为后续存个体状态留路。建议 v1 `stacksTo(16)` 折中。
3. **吃/放走冲突**：看着方块想吃——潜行反转（推荐）或"看着方块恒放走，想吃抬头"。
4. **自动拾取默认态**：默认**关** + filter 默认空=全部（模型开工具时自己声明）。
5. **捕获成功率/冷却**：v1 = 100%、无冷却。
6. **capture 归组**：interact（本方案）或 item？按"对实体做动作"归 interact 更顺。
